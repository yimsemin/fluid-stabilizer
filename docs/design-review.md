## 0. 요약

이 아이디어는 **정당한 Physical AI 문제**다. 단, 플랜트가 반응형 규칙기반 제어가 실패하는 조건이 되도록
의도적으로 맞춰졌을 때만 그렇다. 순진하게 두면, 손으로 쓴 "액체 표면에서 느낀 가속에 수직으로 유지"
컨트롤러가 대부분을 풀어 버리고 RL 이 증명할 것이 별로 없다.

주요 권장:

1. **슬로시 모델에 입자 유체(SPH/FLIP)나 PhysX 관절 진자를 쓰지 마라.** 직접 적분하는 **등가역학 모델**
   (축당 진자 1개, 분석적 적분)을 인터페이스 뒤에 두어, 나중에 얕은물 모델로 바꿔 끼울 수 있게 한다.
   이유: 결정론, 속도, 보정, RL 스텝 예산.
2. **Unity ML-Agents 를 backbone 으로 채택하지 마라.** 센서/액추에이터 메시지 경계를 깨끗하게 유지하고,
   학습기를 교체할 수 있게 한다. ML-Agents 를 쓰더라도 어댑터 뒤에 둔다.
3. **베이스라인 컨트롤러를 먼저 만들어라**(specific-force alignment, 튜닝된 PID, 특권 full-state
   MPC/LQR). 이것들이 바닥과 천장을 정한다. RL 이 PID 바닥 위로 의미 있게 올라가지 못하면 과제나 시뮬이
   잘못된 것이다. 6개월 뒤가 아니라 2주차에 알아야 한다.
4. **잔차 RL 을 써라.** 정책이 분석적 베이스라인 위에 얹는 보정을 출력한다. 멀쩡한 바닥을 보장하고, 어려운
   잔차(슬로시 상태, 액추에이터 지연/한계, 플랜트 변동)에 학습을 집중시킨다.
5. **지연, 이산시간 제어, 센서 노이즈/바이어스, 액추에이터 비이상성을 첫날부터 모델링하라.** 이것들이
   sim-to-real 의 걸림돌이고 넣는 비용은 싸다.
6. **비대칭 actor-critic 을 써라.** critic 은 ground truth 를 보고 actor 는 센서만 본다. 인터페이스로
   강제해서, actor 가 문자 그대로 ground truth 를 호출할 수 없게 한다.
7. **정밀도 예산은 차량이 아니라 액추에이터에 써라.** AI 가 제어하는 것은 액추에이터다. 차량에서는 *믿을 만한
   베드 운동*만 있으면 된다.

## 1. 이것이 적절한 Physical AI 학습 문제인가?

**조건부로 그렇다.** 제어 문제를 RL 로 풀 가치가 있게 만드는 요소를 갖추고 있다.

- **진짜 부분 관측성.** 액체 CoM, 슬로시 모드 진폭, 기울어지는 차량에서 중력과 가속을 분리하는 것은 직접
  측정할 수 없다.
- **자명하지 않은 시간 동역학.** 슬로시는 약하게 감쇠하는 진동자다. ring-down 이 기동보다 오래 이어지고,
  제어 행동이 미래의 상태를 만든다.
- **역결합.** 움직이는 액체가 탱크의 CoM 과 액추에이터가 느끼는 토크를 바꾼다. 플랜트가 상태에 따라 달라진다.
- **비이상적인 액추에이터.** rate/torque 한계, 전송 지연, 백래시 때문에 순수한 반응만으로는 안 되고
  예측해야 한다.
- **예측할 수 없는 외부 외란**(인간 운전자).
- **플랜트 불확실성**(fill 레벨, 액체 특성, 액추에이터 마모). 고정 gain 보다 적응하는 정책이 유리하다.

**조건:** 위 항목 각각이 의미 있을 만큼 강해야 한다. 액추에이터가 빠르고, 탱크가 강체이고, freeboard 가
넉넉하고, 슬로시가 많이 감쇠하면, 문제는 "탱크를 느낀 중력 벡터에 맞추기"로 무너지고 학부 제어 실습이
RL 을 이긴다. §2, §12 참고.

**정직하게 유지할 프레이밍:** 여기서 RL 의 현실적인 기여는 *적응형 외란 거부와 슬로시 상태 추론*이지 "무에서
제어를 발견하는 것"이 아니다. 그것도 진짜 Physical AI 의 결과다. 그 이상으로 부풀리지 마라.

## 2. 규칙기반 컨트롤러가 대부분을 풀 것인가?

**리스크: 높다. 플랜트를 그에 맞서도록 맞추지 않는다면.** 가장 뻔한 베이스라인은 이렇다.

> 탱크 IMU 에서 탱크 프레임의 specific-force 벡터 **f = a − g** 를 추정한다(슬로시가 일으킨 가속을
> 거르도록 저역통과). 탱크 바닥이 **f** 에 수직이 되도록 탱크 자세를 명령한다. 명령에 rate 제한을 걸고,
> 슬로시 고유주파수에 notch 필터를 더해 명령이 슬로시 모드를 여기하지 않게 한다.

이 컨트롤러는 진자를 흉내 내는 것이며 준정적이거나 느린 기동에서는 정말로 잘 동작한다. `(탱크 틸트 오차,
탱크 자이로)` 에 대한 튜닝된 PID 는 더 낫다. 둘을 합치면 완만한 운전부터 중간 정도의 운전까지는 스필을
막을 가능성이 높다.

**규칙기반 제어가 무너지는 곳 — 그리고 RL 이 값을 하는 곳:**

| 조건 | 규칙기반이 어려운 이유 |
|---|---|
| 액추에이터의 rate/torque 가 외란 대역폭에 비해 제한적 | 가속을 *느끼고* 움직이기 시작했을 때는 이미 늦다. 외란의 추세와 운전자 의도 신호에서 예측해야 한다 |
| 슬로시 공진 | 순진한 틸트 추종은 특정 기동 주파수에서 슬로시 모드에 에너지를 펌핑한다. 능동 슬로시 감쇠가 필요한데 이는 틸트 추종 목표와 충돌한다 |
| 액추에이터 지연 + 백래시 | 고정 gain 피드백은 백래시 dead zone 근처에서 불안정하거나 채터링한다. 학습된 보상기가 필요하다 |
| 숨겨진 슬로시 상태 | IMU 만 쓰는 feedforward 로는 불충분하다. 내부 observer 나 메모리가 도움이 된다 |
| 플랜트 변동 (fill, 감쇠, 마모) | gain 하나로는 타협일 수밖에 없다. 이력에서 플랜트를 추론하는 적응 정책이 이긴다 |
| *새* 기동이 시작되는데 이전 기동의 ring-down 이 진행 중 | 위상이 중요한 중첩된 슬로시 모드라 손으로 튜닝하기 어렵다 |

**설계에 넣은 완화책:**

- **첫 슬로시 고유주파수(~0.4~1.2 Hz)** 가 실제 트럭 기동과 트럭-서스펜션 공진 대역에 겹치도록 탱크
  기하를 고른다.
- **폐루프 대역폭(~2~5 Hz)** 과 **rate 한계** 를, 공격적인 운전에서 예측이 반응을 이길 만큼 낮은
  액추에이터로 고른다.
- 짐벌 피벗을 **탱크 CoM 근처**(중립 안정)에 둔다. 그러면 자유로운 짐벌이 정적 케이스를 수동으로 풀어
  버리지 *않아서* 능동 제어가 실제로 필요해진다. 의도적인 선택으로 문서화한다.
- **freeboard**(정지 상태 액면 위 rim 높이)를, 공격적인 운전에서는 스필이 생길 수 있고 완만한 운전에서는
  생기지 않을 만큼 작게 한다.
- 고정 gain 컨트롤러 하나가 최적이 되지 않도록 플랜트를 **도메인 랜덤화**한다.
- **잔차 RL** 을 써서 비교가 명시적으로 "베이스라인" 대 "베이스라인 + 학습된 보정"이 되게 하고, RL 의
  어떤 승리든 명확히 드러나게 한다.

**방법론적 규칙:** 분석적 + PID 베이스라인은 산출물이지 버릴 것이 아니다. 모든 RL 결과는 그것들, 그리고
특권 full-state MPC(성능 천장, §12)와 비교해서 보고한다.

## 3. 슬로시 시간 동역학을 진짜 학습 문제로 만들려면 무엇이 필요한가?

1. **준정적 CoM 이동이 아니라 진짜 동역학을 가진 슬로시 모델.** 최소한 축당 **1차 모드의 고유주파수와
   감쇠비**, 그리고 탱크에 가하는 힘/모멘트 반응을 표현해야 한다.
2. **양방향 결합.** 슬로시의 반응 힘/토크가 탱크 강체와 작동 관절(변하는 하중 토크)에 작용해야 한다.
3. **actor 에게는 숨겨진 슬로시 상태.** 정책은 탱크 IMU, 모터 전류, 로드셀 이력에서 상태를 추론해야 한다.
   그러면 메모리(프레임 스택이나 recurrent)가 필요해지고 내부 observer 가 보상받는다.
4. **슬로시 대역과 겹치는 외란 스펙트럼.** 기동이 공진을 여기할 수 있어야 하고, "언제 움직일 것인가"가
   자명하지 않아야 한다.
5. **ring-down 을 담을 만큼 긴 에피소드.** 마지막 기동 뒤에도 슬로시 주기가 여러 번 이어져야 액체에 에너지를
   남기는 비용이 느껴진다.
6. **스필 이벤트뿐 아니라 슬로시 에너지와 rim 근접 여유도 벌하는 reward**(§11). 그래야 세밀한 연속 제어가
   보상받는다.
7. 일부 에피소드의 **미리 여기된 초기 조건**(t=0 에 액체가 이미 움직이고 있음). 정책이 차분한 시작을
   가정하지 못하게 한다.

## 4. 브리프가 언급하지 않은 중요한 물리 / 변수

- **Freeboard / rim 높이.** "넘치는가"를 가르는 가장 중요한 단일 기하 파라미터다. 명시적이고 랜덤화된
  파라미터여야 한다.
- **슬로시 고유주파수와 감쇠비를 일급 파라미터로.** 브리프는 "액체량"을 나열하지만, 그것이 만드는 동적
  응답은 나열하지 않는다.
- **차량 서스펜션.** 트럭 베드는 도로를 직접 보지 않는다. 서스펜션이 ~1~2 Hz 공진을 가진 저역통과로서
  탱크가 느끼는 외란의 *모양을 바꾼다.* 최소한 단순한 스프렁매스로 모델링해야 한다.
- **중력/가속 모호성.** IMU 는 specific force **f = a − g** 를 측정한다. 기울어지는 트럭에서 운동과 중력을
  분리하려면 자세 추정기가 필요하다. 이것을 문제에 남겨 둔다. 정책에 깨끗한 중력 벡터를 **주지 마라.**
- **액추에이터의 유지 토크(열 한계).** 긴 언덕에서는 액추에이터가 기울어진 탱크를 중력에 맞서 무한정
  버틴다. 연속 토크 한계 ≠ 피크 토크다. 둘 다 모델링해야 한다. 안 하면 실제 모터가 과열된다.
- **2축 운동학 결합.** 회전 순서가 중요하고 ±90° 근처에서 축이 퇴화한다. 최대 travel 을 90° 보다 훨씬
  작게(≈ ±25~35°) 유지하고 회전 순서를 고정한다.
- **회전/swirl 슬로시.** 정사각형에 가깝거나 원통형인 탱크에서 생긴다(대각선 방향 여기가 회전 파동을
  구동한다). 실재하고 어렵다. **v1 에서는 피하고**, 뚜렷하게 직사각형인 탱크(aspect ratio ≥ ~1.6)를 쓴다.
- **연속적인 스필 측정.** "넘쳤다/안 넘쳤다"는 reward gradient 로는 너무 희소하다. 스텝당 overflow 부피가
  필요하다.
- **구체적 모델로서의 센서 결함.** 노이즈 밀도, 바이어스, 바이어스 random walk, scale-factor 오차, 축
  오정렬, 양자화, 갱신율, 지연, jitter, dropped frame. "현실적인 센서"는 숫자여야 한다. 아니면 정책이 깨끗한
  데이터에 과적합한다.
- **제어/작동 지연과 그 jitter.** 피드백 제어에서 sim-to-real 갭 1순위다.
- **시간 척도의 분리.** 물리/슬로시 적분, 센서 샘플링, 제어를 Unity 프레임레이트에 맡기지 말고 명시적으로
  설계한다. (v1 값은 600/200/100 Hz — [frames-units-conventions.md](frames-units-conventions.md).)
- **탱크↔차량, IMU↔body 의 장착 오정렬**(작은 미지의 회전과 오프셋). 고전적인 현실 갭이고 랜덤화하기도
  쉽다.
- **운전자-in-the-loop 데이터 문제.** 사람이 10^8 학습 스텝을 운전할 수는 없다. 합성 운전자 프로파일이
  실제 입력 분포를 덮어야 하고, 그렇지 않으면 정책이 과적합한다(§14, §17).

우선순위가 낮거나 미룰 수 있는 것: 배플과 다중 격실 탱크, 마운트 구조의 컴플라이언스, 타이어 slip 동역학,
공력, 열/배터리 droop, 파도 깨짐 / 공기 혼입 / 표면장력.

## 5. 반드시 모델링할 것 vs 건너뛰어도 되는 것

### 반드시 모델링 (v1)

- 단순한 서스펜션을 가진 스프렁매스로서의 차량 → 현실적인 6-DOF 베드 운동.
- 2-DOF 작동 짐벌 위의 강체로서의 탱크. 피벗은 탱크 CoM 근처.
- 축당 올바른 1차 모드 고유주파수와 감쇠를 가진 reduced-order 슬로시 모델. 탱크와 관절에 대해 양방향 결합.
- 축당 액추에이터: 2차 응답 또는 모터 + 기어박스, 토크 포화(피크 + 연속), rate 한계, travel 한계, 백래시
  dead zone, Coulomb + 점성 마찰, 전송 지연.
- 구체적인 노이즈/바이어스/지연/갱신율을 가진 센서: 차량 IMU, 탱크 IMU, 로드셀 3~4개, 관절 엔코더 2개,
  모터 전류 추정 2개. 선택적으로 점 액체 레벨 센서 1~3개.
- 연속적인 스필 측정(스텝당 overflow 부피).
- grade, bank, 거칠기(사인 + 이산 스텝)를 가진 도로.
- 현실적인 고정 갱신율의 이산시간 제어 루프와 zero-order hold.
- 모든 확률 요소에 seeded RNG, 고정 timestep.

### 건너뛰어도 됨 (v1)

- 입자 유체(SPH/FLIP), CFD.
- 파도 깨짐, 물보라, 표면장력, 공기 혼입.
- 배플, 다중 격실 탱크. *(배플은 F16 에서 얕은물 모델에 구현했다.)*
- 회전/swirl 슬로시(탱크 aspect ratio 로 회피).
- 마운트 구조의 컴플라이언스.
- 상세한 타이어 모델 / 타이어 slip(friction-circle 점 모델을 쓴다).
- 공력, 온도, 배터리 droop.
- 사실적인 액체 렌더링(단순한 시각적 프록시로 충분하다).
- yaw 또는 수직(heave) 안정화 축 — 2축 회전이 맞는 범위다.
  *(참고: heave 는 이후 D6 에서 외란 전달 경로로 추가됐다. 안정화 축은 아니다.)*

## 6. 액체 슬로시 구현 옵션 비교

| 옵션 | 물리적 타당성 | 계산 비용 | RL 적합성 | 구현 난이도 | 판정 |
|---|---|---|---|---|---|
| **A. 준정적 CoM 이동** (평형 표면의 점질량) | 없음 (동역학이 없다) — 핵심 요구에 위배 | 무시할 만함 | 해당 없음 | 자명 | **sanity check 용으로만**, 모델로는 안 쓴다 |
| **B. 등가역학 모델** — 축당 진자(또는 spring-mass) 1개, 분석적 적분, 양방향 결합 | fill 20~80 %, 저~중 진폭, 1차 모드가 지배적인 경우에 높다. 잘 검증됨 (NASA SP-106, 자동차 탱크 슬로시 제어 문헌) | 무시할 만함 (ODE 상태 2~4개 추가, 폐형). 500 Hz 이상도 쉽다 | **훌륭하다** — 결정론적, 빠르고 안정적이며, 파라미터가 도메인 랜덤화에 1:1 로 대응한다 | 중간 | **v1 권장** |
| **C. 다중모드 modal ROM** — 직사각형 탱크의 처음 N개 분석적 슬로시 모드를 겹침, 각각 감쇠가 있는 구동 진동자 | 더 큰 진폭 / 다중 주파수 여기에서 더 낫다. 여전히 선형에 가깝다 | 낮음 (N × 옵션 B) | 매우 좋다 | 중~높음 (모드 형상이 필요) | **2단계 업그레이드 권장** — B 와 같은 인터페이스 |
| **D. 높이장 위의 얕은물(Saint-Venant)** — 깊이평균 2D 솔버, 탱크 가속도를 체적력으로 | 얕거나 중간 정도의 깊이에서 좋다. 진행하는 파동, hydraulic jump, 공간적 표면, 스필 위치를 포착한다. 수직 가속, 파도 깨짐, 심해 분산은 놓친다 | 낮음~중간: 64×32 격자는 CPU 에서 수백 Hz 로 싸다 | 조심하면 좋다. 상태가 크고, 결정론을 위해 고정 dt 와 스레딩 경합 없음이 필요하다. 솔버가 불안정해져 학습을 방해할 수 있다 | 중~높음 (안정적인 CFL 제한 스킴이 필요) | **2/3단계 정밀도 옵션으로 권장.** rim overflow 와 레벨 센서를 직접 준다 |
| **E. SPH / FLIP 입자 유체** | 시각적으로 최고. 노이즈가 많고 비결정론적이며 파라미터에 취약하다. 실제 고유주파수 보정이 어렵다 | 나머지의 10~100배. RL 스텝 예산을 깬다 | **나쁨** — 비결정론이 재현성을 깬다. 학습과 GPU 를 두고 경합한다 | 높음. 서드파티 라이선스/의존성. sim-to-real 보정은 추측에 가깝다 | **학습에는 거부.** 선택적으로 오프라인에서 한 번 돌려 B~D 를 튜닝/검증하는 용도 |
| **F. 다중 강체 "ball pit"** (탱크를 작은 PhysX 구로 채움) | 파동 물리와 감쇠가 틀리고 노이즈가 많다. 고유주파수를 맞추는 것은 편법이다 | 중~높음 | 나쁨 (PhysX 솔버 노이즈, 비결정론) | 낮음~중간 | **거부** |

### 권장

**B** 로 시작한다. `ISloshModel` 인터페이스를 정의해서 **C** 와 **D** 를 액추에이터·센서·컨트롤러 층을
건드리지 않고 바꿔 끼울 수 있게 한다. RL 수치를 믿기 전에 B/C/D 를 **E** 또는 공개된 슬로시 데이터와
비교해 검증한다.

**옵션 B 의 주의점:** 액체가 rim 을 넘었는지는 직접 알 수 없다. `진자 각 + fill 레벨 → rim 가장자리에서의
표면 피크 → overflow 부피` 로 스필을 추정한다. 이 매핑은 근사이므로 일찍 정하고 얕은물 실행과 비교해
검증한다. 옵션 D 는 스필을 직접 준다. 2단계에서 D 로 가는 진짜 이유다. *(구현 결과: D3~D4, findings F3
참고.)*

## 8. 차량 물리 모델 — 적절한 정밀도

**판정: 중-저. AAA 급 차량 시뮬을 만들지 마라.** AI 는 운전하지 않는다. 탱크 베이스의 믿을 만한 6-DOF
운동만 필요하다.

권장:

- 단순한 axle/서스펜션 위의 **3-DOF 스프렁매스 모델**(heave, pitch, roll). 구동 입력:
  - **friction circle 을 가진 점질량 "bicycle" 모델**의 종방향 가속(그래서 강한 제동/코너링이 현실적으로
    plateau 한다),
  - 조향각과 속도에서 나오는 횡방향 가속,
  - 도로 프로파일에 의한 수직 여기,
  - axle/좌우 사이의 하중 이동.
- **Unity `WheelCollider` 보다 직접 만든 스프렁매스 모델을 선호한다.** WheelCollider 는 까다롭고 버전에
  민감하며, AI 가 전혀 건드리지 않는 서브시스템에서 결정론 리스크를 만든다.
- **도로**는 파라미터화된 grade + bank + 거칠기(사인의 합 + 이산 범프 / washboard)로 한다.
- **운전자 입력**은 `IDriverInput` 인터페이스 뒤에 둔다: 사람 구현(키보드/게임패드) + 학습용 스크립트/확률
  프로파일 + 녹화한 사람 트레이스.

*원하는* 정밀도: 베드 가속과 틸트의 올바른 정상상태·과도 크기, 서스펜션 공진.
원하지 *않는* 정밀도: 타이어 열 모델, differential/driveline 세부, 공력.

## 9. 스태빌라이저 액추에이터 모델 — 적절한 정밀도

**판정: 높음. 정밀도 예산을 여기에 쓴다.** AI 가 제어하는 대상이고, 주된 sim-to-real 리스크이며, 모델링이
싸다(축당 상태 몇 개).

축별로 모델링할 것:

- **명령 인터페이스:** 목표 각도 **또는** 목표 rate(권장) **또는** 토크. §11 참고.
- **구동계:** 보정된 2차 폐루프(대역폭 ~2~5 Hz, 감쇠 ~0.7) **또는** 명시적인 모터 + 기어박스:
  `τ_motor = Kt·i`, 전류 제한, 전압 제한(back-EMF → 속도에 따른 토크 상한), 기어비 `N`, 효율 `η`,
  reflected inertia.
- **하드 한계:** 피크 토크, **연속(열) 토크**, 최대 rate `ω_max`, travel `±θ_max`(soft end-stop).
- **백래시:** 방향이 바뀔 때의 dead zone `±δ`. 출력이 dead band 를 거치며 명령보다 뒤처진다.
- **마찰:** 관절의 Coulomb + 점성.
- **전송 지연:** 명령 수신에 `τ_d` ≈ 10~50 ms (버스 + 계산).
- **하중 민감도:** 유효 관성 = 탱크 관성 + 슬로시 반응. 슬로시 반응 토크가 관절에 작용하면 자동으로 따라온다.
  브리프가 원하는 "같은 명령, 다른 결과"가 바로 이것이다.
- **액추에이터 센서:** 출력 엔코더(12~16비트 양자화, 약간의 노이즈), 모터 전류(노이즈가 있고 명령 토크에
  비례) — 액추에이터가 "느끼는 하중", 슬로시 반응의 프록시.

이 숫자들은 하드웨어가 생기기 전에 **실제 후보 서보/기어모터의 데이터시트**에 맞춰 보정한다.

## 10. 센서 구성 — 현실성 평가

제안된 센서 구성은 잘 골랐고 현실적이다. 센서별 평가:

| 센서 | 현실적인가? | 유지? | 메모 |
|---|---|---|---|
| 차량 IMU (accel + gyro) | 예 | 예 | 노이즈/바이어스/random-walk/지연을 추가한다. ~100~400 Hz |
| 탱크 IMU (accel + gyro) | 예 | 예 | 슬로시가 일으킨 틸트와 탱크 운동을 감지한다. 같은 결함 모델. 별도의 장착 오정렬 |
| 로드셀 | 예 | 예 — 배치 패턴으로 **3~4개** | 하나는 총 무게(쉽다). 3~4개는 *실제 장비가 하는 방식대로* 부분적인 CoM 을 추정한다. 반칙 없이 부분 슬로시 관측성을 준다 |
| 스태빌라이저 엔코더 | 예 | 예 — 필수 | 축당 출력 측 각도. 양자화 |
| 모터 전류 / 토크 추정 | 예 | 예 | 슬로시 반응 하중의 프록시. 가치 있음 |
| 제한적인 액체 레벨 센서 | 고정 위치의 **점** 센서(float / 초음파 / 정전용량 로드)일 때만 | 선택, 1~3점 | 탱크 중심의 초음파 센서 하나는 국소 표면 높이를 읽는다. 슬로시에 심하게 오염되지만 이것이 *유용한 신호*다. 전체 레벨 필드는 **비현실적**이므로 금지 |

**추가를 고려할 것:**

- **차량 속도 / 바퀴 속도**(차량 CAN). 현실적이고 싸며 도움이 많이 된다(`a_lateral ≈ v²·yawrate`).
  **추가를 권장한다.**
- **조향각 + throttle/brake 위치**(차량 CAN). 실제 트럭에서 현실적이다(OBD/CAN). 경계선에 있다. 외란의
  부분적 *preview*("운전자의 의도")이기 때문이다. 실제 배포 환경에는 이것이 있다. **선택적 관측 플래그를
  권장한다.** 있을 때와 없을 때 각각 학습해서 정책이 얼마나 의존하는지 측정한다.
- **전방 도로/카메라 preview.** 브리프가 미래 도로 정보를 명시적으로 제외했다. **v1 에서는 존중한다.** 다만
  look-ahead 센서가 가능하게 하는 preview 제어가 가장 큰 잠재적 성능 이득이다. v1 기능이 아니라 훗날의
  ablation 으로 표시해 둔다. *(소유자가 D12 에서 프리뷰를 쓰지 않는 원칙으로 확정했다. 후속 프로젝트의
  질문이다.)*

**제거할 것:** 없음. **중복이라 건너뛸 것:** 탱크 barometer/inclinometer (IMU 융합이 덮는다).

## 11. 관측 / 행동 / Reward 후보

### 관측 (actor) — 모두 센서에서 나오고, 노이즈가 있고, 지연된다

- 차량 IMU: 3축 accel + 3축 gyro (body 프레임)
- 탱크 IMU: 3축 accel + 3축 gyro (탱크 프레임)
- 관절 상태: 각도 2개, rate 2개(엔코더 차분), 모터 전류 2개
- 로드셀: 스칼라 3~4개
- 선택: 점 액체 레벨 1~3개
- 선택 플래그: 차량 CAN (속도, 조향, throttle, brake)
- **마지막 행동(들)** — 지연/백래시 보상에 필수
- 허용되는 유도 특징(온보드에서 계산 가능): 탱크 프레임에서 저역통과한 specific-force 방향과 그 최근 변화율
- **메모리:** 최근 5~10 제어 스텝의 프레임 스택, 또는 recurrent hidden state — 슬로시 상태 추론에 필수

**actor 관측에 절대 들어가면 안 되는 것:** 실제 액체 CoM, 입자 위치, 실제 슬로시 모드 진폭, 실제
자세/속도, 미래 도로, 미래 운전자 입력, 물리 내부 상태. 이것들은 critic 과 로깅에만 쓴다.

### 행동

- **v1 권장:** 축당 관절 **각속도** 명령(값 2개)을 저수준 액추에이터 컨트롤러가 적분한다. 스텝 형태의 각도
  명령보다 매끄럽고 채터링을 피한다. (목표 각도 명령도 대안으로 허용된다.)
- **토크 명령:** 하드웨어에 가장 충실하지만 학습이 가장 어렵고 가장 안전하지 않다. 고급 옵션이며 v1 에는
  쓰지 않는다.
- **강력 권장: 잔차 행동.** 행동 = 분석적 베이스라인 명령 + 학습된 보정. 멀쩡한 바닥을 보장하고, 어려운
  잔차에 학습을 집중시키며, "RL 이 PID 를 못 이긴다"는 리스크를 없앤다.
- 항상 **action-rate 페널티**를 넣는다.
- *(구현: 관절 각속도 + 잔차로 시작했으나, 잔차 액션 공간이 학습 신호가 없는 절벽이어서(F9) 명시적 잠금
  액션을 가진 lock-capable 합성으로 바뀌었다 — D8·D10, 계약은 D9.)*

### Reward (스텝당, 연속)

```
r = − k1 · overflow_volume                     (1차)
    − k2 · near_rim_margin_cost                 (표면 피크가 rim 에 가까워질수록 커지는 매끄러운 비용)
    − k3 · slosh_kinetic_energy                 (액체를 능동적으로 감쇠하면 보상)
    − k4 · |action_rate|
    − k5 · actuator_effort (|torque| 또는 power)
    − k6 · joint_limit_proximity_cost
    − k7 · |tank_tilt_relative_to_vehicle|      (선택, 작게 — 과격한 곡예를 억제)
    + k8  (작은 alive 보너스, 선택)
    − K_term  큰 스필 이벤트에 대해 (종료)
```

커리큘럼: 완만한 운전자 프로파일, 낮은 fill, 넉넉한 freeboard 로 시작해서 학습하는 동안 넓힌다.

**Reward-hacking 감시:** 정책이 탱크를 하드 end-stop 에 부딪쳐 액체를 "가두거나" 슬로시 모델의 아티팩트를
악용할 수 있다. effort / limit-proximity 페널티로 완화하고, 학습에 쓰지 않은 고정밀 슬로시 모델에서 학습된
정책을 검증한다.

### Critic (학습 전용) — 특권 관측

actor 가 보는 모든 것에 **더해**: 실제 슬로시 모드 진폭/속도, 실제 액체 CoM, 실제 specific force, 실제 탱크
자세/속도, 실제 액추에이터 상태. 비대칭 actor-critic 은 학습 속도를 크게 높이고, 배포 시 반칙은 0 이다.

## 12. 시간 상태를 위한 AI 아키텍처

- **메모리가 필수**(숨겨진 슬로시 상태). 진행 순서:
  1. **프레임 스택 + MLP, PPO** — 여기서 시작한다. 종종 충분하다.
  2. **GRU/LSTM recurrent 정책** — 프레임 스택이 한계에 부딪히면.
  3. window 위의 Transformer — v1 에는 과하다.
  4. 명시적으로 학습한 상태 추정기(Kalman / 학습된 observer)를 MLP 앞에 붙인다 — 강력하고 해석 가능한
     옵션이며 sim-to-real 에 좋다.
- **비대칭 actor-critic**(critic 이 ground truth 를 본다). 강력 권장.
- **보조 self-supervised head:** 관측 이력에서 실제 슬로시 상태를 예측한다. 낮은 비용으로 학습된 표현이
  좋아진다.
- **암묵적 시스템 식별**(RMA 방식): 인코더가 최근 이력을 잠재 플랜트 파라미터 벡터로 사상한다. 실제 랜덤화
  파라미터를 보는 특권 인코더로부터 distillation 으로 학습한다. 정책이 배포 시 fill 레벨 / 감쇠 / 액추에이터
  마모에 적응하는 방법이다.
- **알고리즘:** PPO 를 먼저(견고하고 관대하다). 나중에 샘플 효율을 위해 SAC 를 고려한다.

### Unity ML-Agents 에 대해

ML-Agents 는 많은 것을 공짜로 주고(PPO/SAC, Unity↔Python 배관) 비전문 개발자에게 정말 매력적이다. **그러나
학습을 Unity 에 결합시키고, API 가 버전마다 바뀌며, 명시한 Sensor→Controller→Actuator 분리와 ROS 2 목표에
어긋난다.** 나중에 외부 학습기나 실제 로봇을 원하면, 환경이 ML-Agents 에 용접되어 있음을 알게 된다.

**권장:** ML-Agents 를 backbone 으로 **만들지 마라.** 언어 중립적인 env 경계를 정의한다.

- 지금의 C# 컨트롤러를 위한 in-process C# `IController` 이음매(+ 계약을 담는 DTO).
- 외부 Python 학습기(Stable-Baselines3, CleanRL, `rsl_rl`)를 위해 **Gymnasium 스타일** `reset()/step()` API
  를 노출하는 얇은 소켓 / gRPC 브릿지.

브릿지가 나중에 처리량 병목이 되면, *그때* 어댑터 뒤에서 ML-Agents 를 평가한다. 그 전에는 하지 않는다.

### 배포에 대해 — 정책은 별도 프로세스 (소유자 결정 2026-08-29)

완성된 데모는 학습된 정책을 Unity 바이너리에 **굽지 않는다**("ONNX-in-Unity, 런타임 Python 없음" 방식은 쓰지
않는다). 실제 로봇은 몸·뇌·학습 장비가 링크로 대화하는 별개의 것들이므로, 시뮬도 그렇게 본뜬다.

- **Unity = 플랜트** — 세계 + 몸체 + 센서 + 액추에이터. 센서 메시지를 발행하고 명령 메시지를 소비한다. ①
  강체는 여기에 있는 기계적 설정이다. ② 규칙기반은 엔진프리 `IController`(지금은 in-process, 이식 가능)다.
  학습 정책은 여기에 **들어 있지 않다.**
- **정책은 자기 프로세스**(`serve_policy.py`)에서 돌며, 학습 때와 같은 length-prefixed TCP 브릿지로
  연결한다. 온보드 컴퓨트 ↔ 센서/액추에이터 링크에 해당한다. Unity 의 `RemotePolicyController`(엔진프리,
  `FluidStabilizer.Rl`)가 클라이언트다. `ObservationEncoder` 를 로컬에서 돌려 인코딩된 벡터를 보내고,
  행동을 받고, 서버가 없으면 잠근 hold 로 되돌아간다.
- **ONNX 는 교환 포맷** — 학습된 체크포인트를 그 프로세스에 넘기는 수단이다. 초안 단계에서는 직접 만든 가중치
  파일도 허용한다.

트레이드오프: 데모가 "Unity 앱 **과** 정책 프로세스를 함께 실행"하는 형태가 된다. 학습 산출물로서는 그것이
요점이다. 전체 근거는 [project-goals.md](project-goals.md) → "최종 제품 아키텍처".

## 13. 도메인 랜덤화 대상

에피소드마다(일부는 스텝마다 노이즈로도):

- **액체:** fill ratio(0.3~0.8), 밀도, 1차 모드 고유주파수(±20~40 %), 감쇠비(×0.3~3), 참여 질량 비율.
- **탱크:** 빈 질량, 관성 텐서, freeboard / rim 높이.
- **액추에이터:** 피크 & 연속 토크, rate 한계, 대역폭, 백래시 폭, 전송 지연(10~50 ms), Coulomb + 점성
  마찰, 기어 효율.
- **센서:** 노이즈 σ, 바이어스, 바이어스 random-walk 율, scale-factor 오차, 축 오정렬, 추가 지연, 갱신율
  jitter, 양자화 단계, 가끔 dropped frame.
- **기하:** 탱크↔차량 장착 오정렬, IMU 장착 회전/오프셋.
- **차량:** 질량, CoG 높이, 서스펜션 강성/감쇠.
- **도로:** grade, bank, 거칠기 스펙트럼, 이산 범프의 크기/간격.
- **운전자:** 프로파일의 공격성, 반응 시간 노이즈, 입력 양자화와 지연.
- **제어 루프:** rate jitter, 가끔 dropped command.
- **초기 조건:** 미리 여기된 슬로시 상태.

커리큘럼: 명목값 근처에서 시작해서 학습하는 동안 넓힌다. 나중의 분석을 위해 모든 에피소드에서 샘플한
파라미터를 기록한다.

## 14. Sim-to-real — 첫날부터 할 것

- **지연 예산.** 모든 지연(센서 획득, 버스, 계산, 작동)을 모델링하고 기록하며 랜덤화한다. 피드백 제어에서
  현실 갭 1순위다.
- **이산시간 제어**를 현실적인 고정 임베디드 주기(50~100 Hz)로 하고, 행동은 zero-order hold 로 유지한다.
  연속시간이라는 반칙은 없다.
- **어디서나 단위, 프레임, 타임스탬프.** SI 단위. 오른손 프레임을 한 번 정의한다
  (`frames-units-conventions.md`). 모든 센서 샘플이 타임스탬프를 갖고, 컨트롤러는 프레임 카운트가 아니라
  타임스탬프로 동작한다.
- **액추에이터와 센서 모델을 후보 부품의 실제 데이터시트에 맞춰 보정한다** — 지금.
- **비대칭 정보는 actor 밖에** 둔다. 인터페이스로 강제한다.
- **도메인 랜덤화 + 암묵적 시스템 ID** 를 전이 수단으로 쓴다.
- **모든 것을 재생 가능한 ROS-bag 호환 스키마로 기록한다.** ROS 가 없어도, 나중에 실제 로그를 같은
  컨트롤러로 재생할 수 있도록.
- **컨트롤러는 정의된 메시지 API 를 가진 별도 모듈/프로세스**로 둔다. 같은 컨트롤러 바이너리가 지금은 시뮬
  에서, 나중에는 ROS 2 브릿지에서 코드 변경 없이 돌아야 한다.
- **현실 갭 테스트:** 홀드아웃 운전자 트레이스, 홀드아웃 도로 프로파일, 그리고 결정적으로 — 정책이 학습한 적
  없는 *다른 슬로시 모델 클래스*(얕은물)에서의 평가. 모델 클래스가 바뀌어도 버티는 것이 현실에서 버틸지에
  대한 가장 좋은 싼 예측 지표다.
- **안전 봉투**(각/rate/토크 제한)는 정책이 아니라 저수준 액추에이터 층에 둔다. 정책이 실제 장비가 거부할
  명령을 내릴 수 없게 한다.

## 15. ROS 2 / 최소 재구조화 계획

지금 ROS 층을 **만들지 마라.** 그렇다고 막지도 **마라**:

- **지금은 메시지 DTO** 를 둔다. 나중의 ROS 2 메시지와 1:1 로 대응하는, 직렬화 가능한 평범한 C# struct 이며
  가능하면 `sensor_msgs` 와 필드명/타입이 같다: `VehicleImu` ↔ `sensor_msgs/Imu`, `TankImu` ↔
  `sensor_msgs/Imu`, `JointState` ↔ `sensor_msgs/JointState`, + `LoadCells`, `MotorState`, `LevelSensors`,
  `StabilizerCommand`.
- **메시지 버스 인터페이스** — 지금은 in-process 구현, 나중에는 ROS 2 구현(`ros2-for-unity` 또는 외부 브릿지
  프로세스). ROS 2 의존성은 Unity 프로젝트 밖에 둔다. 하드웨어가 연결될 때만 별도의 `ros2_ws/` 가 생긴다.
  *(현재 구현: 명시적인 `IMessageBus` 타입은 아직 없고 `IController` 이음매 + DTO 가 계약을 담는다.)*
- **컨트롤러는 `UnityEngine` 참조 0.** 평범한 C# 라이브러리(또는 Python)로, 메시지를 받고 메시지를 낸다.
  나머지가 동작하게 만드는 유일한 하드 룰이다.
- **`IClock` 추상화**(지금은 sim time, 나중에는 wall time)와 고정 주기 스케줄러.
- 전역 가변 상태 없음. 모든 것에 타임스탬프.

이것이 "미래 대비" 예산의 전부다. 그 이상은 과도한 추상화다.

## 17. 학습 환경 vs 수동 주행 테스트 환경

`IDriverInput` 구현으로 선택되는 두 프론트엔드를 가진 하나의 `SimulationCore` 를 쓴다.

| | 수동 주행 / 테스트 | 학습 |
|---|---|---|
| 운전자 입력 | 키보드 / 게임패드, 실시간 | 스크립트 + 확률 운전자 프로파일; 재생한 사람 트레이스 |
| 렌더링 | 켬 | 끔 (헤드리스) |
| 시간 | 실시간 | 시간 스케일, 병렬 인스턴스 여러 개 |
| 목적 | 정성적 테스트, 데모, **사람 트레이스 녹화** | 정책 최적화 |
| Ground-truth 로깅 | 전체 | 전체 (critic + 평가용) |

- **결정론 필수:** 고정 timestep, 모든 확률 요소에 seed 가능한 RNG, 프레임레이트에 의존하는 로직 없음. 이것이
  없으면 RL 을 디버깅할 수 없고 평가를 믿을 수 없다.
- **평가 env:** 헤드리스, ground truth 전체 로깅, 같은 시나리오에서 분석적 베이스라인과 특권 MPC 를 병렬로
  실행해 직접 비교한다.
- **사람 운전 세션을 녹화**해서 고정된 홀드아웃 테스트 셋 *과* 학습용 실제 외란 데이터로 쓴다. 프로젝트에서
  가장 가치가 높은 데이터다(§14 운전자 문제).

## 18. 추가 실패 모드 ("다시 만들어야 할 것" 목록)

### "처음엔 되다가 나중에 다시 만든다"

1. **슬로시에 PhysX 관절 진자나 입자 유체를 쓴 경우.** 튜닝해서 그럴듯한 결과를 얻고 나서 비결정론적이고
   느리고 보정할 수 없음을 발견한다. 센서와 reward 코드가 이미 그 특성에 의존하게 된 뒤에 슬로시 모델 전체를
   바꿔야 한다. → 첫날부터 `ISloshModel` 뒤에 직접 만든 분석적 ROM 을 둔다.
2. **ML-Agents 를 backbone 으로 쓴 경우.** 깊은 Unity 결합 + API 변동 + ROS 분리 목표와 충돌. → 교체
   가능한 학습기와 깨끗한 env 경계.
3. **결정론을 설계에 넣지 않은 경우.** Unity + PhysX + 스레드 + 가변 dt → 재현할 수 없는 에피소드 → RL 을
   디버깅할 수 없고 평가를 믿을 수 없다. → 고정 timestep, 모든 것에 seed, 슬로시 ODE 는 PhysX 밖에서,
   병렬성은 신중하게 통제한다.
4. **좌표계 / 단위 혼란.** 물리 + 센서 + 컨트롤러가 이미 있는 뒤에 일관된 프레임·단위·타임스탬프를 끼워
   넣는 것은 고통스러운 재작성이다. → 물리 코드 *전에* `frames-units-conventions.md` 를 채운다.
5. **스필을 불리언으로만 정의해서 reward 가 학습되지 않는 경우.** 나중에 연속 overflow 측정을 더하면 슬로시
   모델 안에서 다시 유도하고 모든 reward 가중치를 다시 튜닝해야 한다. → 처음부터 연속 overflow 부피.

### "직관적이지만 목표에는 틀린 것"

6. **정책에 깨끗한 중력 / 자세 / 진짜 specific-force 벡터를 주는 것.** 합리적으로 느껴진다("IMU 가 가속을
   주니까"). 그러나 실제 과제의 핵심인 중력/운동 분리 문제를 지워 버리고 시뮬 성능을 부풀린다. → 원시
   IMU 만 주고, 정책/추정기가 융합한다.
7. **Reward = 스필 이벤트뿐.** 직관적이고 깔끔하지만 희소하고 대부분 0 이며 gradient 가 없다. 정책이 세밀한
   제어를 배우지 못한다. → 여유 + 슬로시 에너지 shaping.
8. **자유롭게 매달린 탱크(피벗이 CoM 위).** 기계적으로 "명백히 맞아" 보이지만 정적 케이스를 수동으로 풀어
   능동 제어가 거의 필요 없어지고, 학습 문제가 증발한다. → 피벗을 CoM 근처의 중립 안정으로 선택한다.
9. **전체 `WheelCollider` 차량 시뮬.** "제대로 된" 물리처럼 느껴지지만 AI 가 전혀 제어하지 않는
   서브시스템에 취약성과 결정론 리스크를 더한다. → 3-DOF 스프렁매스 + friction-circle bicycle 모델.

### "현실적으로 보이지만 RL 에는 틀린 조건"

10. **고정밀 SPH 유체.** 데모에서는 멋지다. 그러나 스텝 예산(10^7~10^8 스텝 필요)을 깨고, 결정론을 깨며,
    실제 고유주파수 보정은 어차피 추측이다.
11. **센서를 깨끗한 Gaussian 노이즈로만 모델링하는 것.** 실제 IMU 에는 바이어스 random walk, scale-factor
    오차, 오정렬, 양자화, dropped frame 이 있다. 깨끗한 데이터 + 백색 노이즈로 학습한 정책은 과적합하고
    하드웨어에서 실패한다.
12. **지연을 "나중에, 하드웨어 단계에서" 추가하는 것.** 지연 없이 학습한 정책은 실제 장비에서 진동하는 고
    gain 동작을 배운다. → 첫 스텝부터 지연을 넣는다.

### Feasibility 브래킷

13. **과제가 너무 쉬울 수 있다** → RL 이 PID 를 절대 못 이긴다. *프로젝트의 가장 큰 리스크.* → 베이스라인을
    먼저 만든다. 액추에이터 대역폭 / 슬로시 주파수 / freeboard / 외란 스펙트럼을 어려운 조건으로 맞춘다.
    잔차 RL 을 쓴다.
14. **과제가 사실상 제어 불가능할 수 있다** → freeboard 가 작은 공격적 운전에서는 *어떤* 컨트롤러도 스필을
    못 막는다. reward 가 전부 음수이고 학습이 무너진다. → 특권 full-state MPC(지연 없음, 완전 관측)가 목표
    시나리오에서 거의 0 스필을 달성하는지 검증한다. 그것이 천장이다. 과제를 PID 바닥과 MPC 천장 사이에
    엄격히 두어야 한다. *(구현 결과: findings F1, F4, F5 — 실제로 이 브래킷 문제에 부딪혔다.)*
15. **합성 운전자 분포가 실제 운전과 맞지 않는 경우** → 정책이 스크립트된 기동에 과적합한다. → 다양한 운전자
    프로파일 생성기와 실제로 녹화한 트레이스에 일찍 투자한다.

## 19. 가장 큰 기술 리스크, 순위

1. **Feasibility 브래킷(너무 쉬움 / 너무 어려움).** RL 이 튜닝된 PID 를 이기지 못하거나 아무것도 스필을
   막지 못하면 프로젝트에 결과가 없다. *(실제로는 "너무 쉬움" 쪽으로 실현됐다. 강체가 이미 강해서 어떤
   제어도 이기지 못했다. 결과는 부정적 결과로 보고했다 — lessons.md.)* 완화: 1단계의 베이스라인 + MPC 천장,
   의도적인 플랜트 튜닝, 잔차 RL.
2. **슬로시 모델 선택.** 잘못 고르면(입자 유체) 스텝 예산과 결정론을 잃고, 너무 단순하면(준정적) 문제가
   사라진다. 완화: 인터페이스 뒤의 분석적 ROM, 고정밀 모델과의 검증.
3. **Sim-to-real 갭.** 지연, 센서 결함, 액추에이터 비이상성, 모델링하지 않은 슬로시 동역학. 완화: 첫날부터
   전부 모델링, 도메인 랜덤화, 슬로시 모델 클래스 사이의 테스트.
4. **결정론 / 재현성.** 없으면 RL 디버깅과 평가를 믿을 수 없다. 완화: 고정 timestep, seeded RNG, 슬로시 ODE 는
   PhysX 밖에서.
5. **운전자 데이터 분포.** 합성 운전자가 실제 입력을 덮지 못한다. 완화: 운전자 프로파일 생성기 + 홀드아웃
   데이터로서의 녹화한 사람 트레이스.
6. **차량 모델의 범위 확대.** AI 가 제어하지 않는 서브시스템에 WheelCollider / 타이어 모델로 시간을 쓴다.
   완화: 고정된 중-저 정밀도 차량 사양.
7. **Reward hacking / 시뮬 아티팩트 악용.** 완화: effort/limit 페널티, 모델 간 교차 검증.

## 20. 1단계 — 무엇을 먼저 구현하나

1. Unity 프로젝트 + 이 문서 세트 + `frames-units-conventions.md` 완성.
2. `SimulationCore`: 고정 timestep 스케줄러, `IClock`, seeded RNG 서비스.
3. 차량: 3-DOF 스프렁매스 + friction-circle bicycle 모델 + 파라미터화된 도로. `IDriverInput` 에 사람
   (키보드/게임패드) 구현 + 스크립트 운전자 프로파일 2~3개 + 트레이스 녹화/재생.
4. 2-DOF 작동 짐벌 위의 강체 탱크, 피벗은 탱크 CoM 근처.
5. `ISloshModel` + 옵션 B 구현(축당 진자 1개, 분석적, 양방향 결합). 연속 overflow 부피 추정.
6. 축별 액추에이터 모델: 모터 + 기어 또는 보정된 2차 응답, + 토크 포화(피크 + 연속) + rate 한계 + travel
   한계 + 백래시 + 마찰 + 전송 지연.
7. 센서 층: 차량 IMU, 탱크 IMU, 로드셀 3~4개, 엔코더 2개, 모터 전류 추정 2개. 모두 구체적인
   노이즈/바이어스/지연/갱신율을 가진다. 메시지 DTO. 플래그 뒤의 선택적 점 레벨 센서.
8. `ISensorBus` / `IActuatorBus` 인터페이스 + in-process 구현. *(현재: `IController` 이음매 + DTO 가
   계약이고, 명시적인 버스 타입은 미뤘다.)*
9. 베이스라인 컨트롤러: (a) specific-force alignment, (b) 튜닝된 PID, (c) 특권 full-state LQR/MPC(천장).
10. 평가 하네스: 고정 시나리오 세트, 스필 + 슬로시 에너지 + effort 지표, 베이스라인 비교, ground truth 전체
    로깅(재생 가능한 스키마).
11. 단순한 시각적 탱크 + 액체 프록시를 가진, 플레이할 수 있는 수동 주행 씬.
12. **하나의** RL 통합 경로: Gymnasium 스타일 소켓 어댑터 + PPO(SB3/CleanRL), 비대칭 critic, 프레임 스택
    관측.
13. 도메인 랜덤화 config(좁게 시작), 에피소드별 파라미터 로깅.
14. 결정이 바뀌면 문서를 동기화해서 유지한다.

**1단계 완료 조건:** 사람이 운전하는 것과 분석적 베이스라인이 탱크를 안정화하는 것을 볼 수 있다. RL 어댑터가
헤드리스 env 에서 PPO 를 끝까지 실행할 수 있다. 평가 하네스가 고정 시나리오 세트에서 PID 바닥과 MPC 천장의
수치를 보고한다.

- 얕은물과 다중모드 슬로시 모델(2단계 — 1단계에서는 인터페이스만). *(실제로는 findings F3 때문에 얕은물을
  1단계로 앞당겼다.)*
- Recurrent / 시스템 ID 정책(2단계).
- 전체 차량 / 타이어 모델, WheelCollider.
