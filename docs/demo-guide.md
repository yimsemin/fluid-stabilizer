## 한눈에

- **무엇:** 사람이 운전하는 트럭에 **뚜껑 없는 물탱크**가 실려 있다. 급제동·
  코너링·범프에 물이 출렁여 넘친다. 탱크 아래 **2축 받침대(스태빌라이저)** 를
  AI 가 제어해서 넘침을 줄이려는 시뮬레이션.
- **AI 는 운전하지 않는다.** 운전자는 AI 가 대응해야 할 외부 교란일 뿐.
- **목적:** "물리 → 센서 → 액추에이터 → 컨트롤러 → 학습 정책 → 평가" 파이프라인
  **전체를 직접 만들며 Physical AI 를 이해**하는 것. 화려한 결과물보다 이해가
  우선. (실제 로봇은 아직 못 사니 시뮬레이션이 로봇을 대신한다.)

## 1. 왜 어려운가 — 슬로시(sloshing)의 시간 동역학

물컵을 들고 걷다 멈춰도 물은 계속 앞뒤로 출렁인다. 이게 문제의 핵심이다:

- **기동이 끝나도 액체는 계속 움직인다.** "지금 가속에 맞춰 탱크를 기울이기"
  같은 반사적 대응으로는 부족하다 — 뒤이어 올 파도를 **예측(anticipation)**
  해야 한다.
- **부분 관측.** AI 는 물 입자 위치나 정확한 무게중심을 볼 수 없다. 실제 센서가
  줄 수 있는 것(IMU, 받침대 각도, 로드셀 등, 노이즈·지연 포함)만 보고 숨은 액체
  상태를 **추론**해야 한다.
- **비이상적 액추에이터.** 받침대 모터는 토크·각속도·각도 한계가 있고, 오래 세게
  쓰면 과열되어 힘이 줄고, 명령에 지연이 있다.

> 반사적 대응이 **오히려 해로울 수 있다:** 파도에 맞춰 탱크를 급히 돌리면
> 슬로시 에너지를 *더* 넣어 넘침이 늘어난다 (아래 F1).

## 2. 구조 — 세 덩어리 + 비교 대상

실제 로봇은 **몸 / 뇌 / 학습 장비**가 분리되어 링크로 대화한다. 시뮬도 그렇게 나눴다.

| 덩어리 | 무엇 | 어디 |
|---|---|---|
| **세계 + 몸** | 차량·도로·탱크·슬로시·액추에이터·센서. 센서값을 내보내고 명령을 받음 | Unity 앱 (`Assets/FluidStabilizer/`) |
| **뇌** | 학습된 정책. 센서값 → 행동 | 별도 Python 프로세스 (`python/serve_policy.py`), TCP 로 연결 (= 나중 ROS 2 자리) |
| **학습 장비** | PPO 강화학습, 행동 복제 | 오프라인 Python (`python/train_ppo.py` 등). 시연과 절대 같이 안 돎 |

물리 계산은 게임 엔진(PhysX)이 아니라 **직접 짠 C# 코드**로 고정 시간간격
(600 Hz)에 적분한다 → Mac/Windows 어디서나 **같은 결과**(결정론), 유닛 테스트
가능, RL 스텝이 빠름.

**비교 대상 (같은 주행을 이 방식들로 처리해 넘친 양을 비교):**

| | 방식 | 한 줄 설명 |
|---|---|---|
| ① | **강체 (Rigid)** | 탱크를 트럭에 볼트로 고정. 스태빌라이저 없음. 바닥선(baseline). |
| ② | **규칙기반** | "느껴지는 기울기에 맞춰 탱크를 반대로 기울여라" 고정 법칙 (화면 표기 "Rule: PID"). |
| ③ | **학습 정책** | 녹화 주행으로 (부분) 학습한 RL. |
| ④ | **후행지식 천장 (hindsight)** | 주행 전체를 미리 다 알고 오프라인 최적화한 저대역(0.1~0.3 Hz) 받침대 궤적. 실제로는 불가능(미래를 알아야 하므로)한 비교용 기준선. 모든 제어기의 이론적 상한은 아니다. |

## 3. 학습은 어떻게 시키나

```
녹화 주행  →  후행지식 천장  →  행동 복제(BC) 웜스타트  →  잔차 RL(PPO)  →  체크포인트  →  serve_policy.py
 (사람이     (미래를 다 알면      (천장 궤적을 흉내내게      (베이스라인 위에      (.pt 파일)     (뇌 프로세스로
  운전)       얼마나 잘하나)        정책망 사전학습)          작은 보정만 학습)                    서빙)
```

1. **녹화 주행** — 플레이 씬에서 `P` 를 눌러 직접 운전한 주행을 파일로 저장
   (`Traces/drive-*.trace.csv`). throttle/brake/steer 만 저장하면 나머지는
   결정론이라 완전히 재현된다. 이게 학습·평가의 단위 = "한 번의 주행".
2. **후행지식 천장 (④)** — 한 녹화 주행에 대해, 주행 전체를 미리 알고 받침대
   궤적을 오프라인 최적화한다. "예측이 완벽하다면 (저대역 궤적으로) 얼마나 줄일 수
   있나"의 기준선. **이게 결정 게이트:** 이 천장조차 강체(①)를 못 이기면, 그 궤적을
   흉내 내는 학습 정책은 못 이긴다 → 전제를 바꾸기 전엔 긴 학습을 하지 않는다.
3. **행동 복제 (BC) 웜스타트** — 천장 궤적을 흉내내도록 정책 신경망을 지도학습으로
   사전 초기화. 처음부터 무작위로 시작하면 탐색이 "F1 절벽"으로 떨어지므로,
   얌전한 시작점을 준다.
4. **잔차 RL (PPO)** — 정책이 **베이스라인(잠근 탱크 등) 위에 작은 보정만**
   강화학습한다. 처음부터 전부 배우는 "맨땅 PPO"는 이 문제를 못 배운다 (아래 설명).
5. **체크포인트 → 서빙** — 학습된 가중치(`.pt`)를 `serve_policy.py` 가 로드해
   별도 프로세스로 추론을 서빙. Unity 는 TCP 로 센서값을 보내고 행동을 받는다.
6. **현재 상태:** 위 파이프라인은 전부 배선·검증됐다. 학습 정책이 강체를 이기지 못한 이유와 결과는
   5절과 [lessons.md](lessons.md).

> **왜 맨땅 PPO 가 안 되나 (F9, [rl.md](rl.md)):** 무작위로 시작한 정책의 짐벌
> 동작이 슬로시를 펌핑해 모든 시도가 일찍 넘쳐 끝난다 → "전부 똑같이 나쁨" 을
> 학습 → 경사가 사라지고 학습이 멈춘다. 좋은 정책은 좁은 "가만히/예측" 능선
> 위에만 있어서 무작위 탐색으로는 못 찾는다.

## 4. 학습된 것 vs 베이스라인 비교

플레이 씬에서 **`C`** 키 → **3분할 화면**. 최신 녹화 주행을 세 트럭이 **동시에**
재생한다:

- 세 트럭 모두 **같은 녹화 주행(같은 조향·제동), 같은 도로**. 다른 건 처리 방식뿐.
- 위 = ① 강체, 가운데 = ② 규칙기반, 아래 = ③ 학습 정책 (`serve_policy.py` 안 켜졌으면
  "(offline → Hold)" 로 강체 폴백).
- 각 칸 패널: **넘친 리터**(크게), rim 근접 시간, 슬로시 에너지 피크, 토크 포화
  시간. 가장 적게 넘친 칸에 **초록 테두리**.
- 세 칸이 다 끝나면 아래에 **한 줄 판정**: "① 강체가 가장 적게 넘쳤다 (…)" 또는
  "레인 간 차이 거의 없음".

**배치 수치:** 메뉴 ▸ *FluidStabilizer ▸ Evaluate Recorded Drives* (또는
*Evaluate Learned Policy*) → 모든 녹화 주행 × 컨트롤러 × 슬로시 모델의 리터 표를
`Logs/trace-eval-<시각>-<id>.txt` 에 쓰고, 에피소드마다 한 줄을 **`Logs/episodes-v2.csv`** 에
덧붙인다 (운영점 + 결과 지표 → 스프레드시트로 누적 비교·그래프).

## 5. 결과를 어떻게 읽나

- **1차 지표 = 넘친 리터.** 부가 지표: rim 근접 시간, 슬로시 운동에너지 피크,
  액추에이터 노력/열부하.
- **헤드라인 벤치마크 = 녹화 주행** (합성 시나리오 아님). 홀드아웃
  주행에서 주행별 리터로 본다.
- **브래킷 규율:** 슬로시 모델 2종 — 싼 **진자 ROM**(학습·빠른 반복용)과
  정밀한 **얕은물 솔버**(검증용). 정책이 진자에서만 이기면 그건 모델
  아티팩트일 가능성이 높다 → 두 모델 모두에서 유지될 때만 인정.

### 말할 결과 — **① 강체가 이긴다**

숫자와 근거는 [lessons.md](lessons.md) "결과", [findings.md](findings.md). 시연에서는 세 문장이면 된다.

1. **반응형 규칙(②)도, 미래를 다 아는 최선의 궤적(④)도 녹화 주행에서는 강체(①)를 못 이긴다**
   (F1·F4·F5·F6). 짐벌에는 속도·토크 한계와 지연이 있어 빠른 도로 외란을 따라가지 못하고, 따라가려다
   오히려 액체를 더 흔든다.
2. **이기는 조건은 있지만 좁다.** 매끄러운 노면의 지속 코너링에서는 천장이 이기고(F8) 학습 정책도
   규칙기반을 51 % 앞선다(F10). 그래도 강체에는 진다. 학습이 안 되던 이유는 하이퍼파라미터가 아니라
   **액션 공간**이었다(F9 → F10).
3. **컨트롤러 대신 탱크를 바꾸면 훨씬 크게 줄어든다** (F15~F17). 충전율을 낮추거나 림을 높이거나 내부
   배플을 넣는 쪽이 능동 제어(−5 ~ −8 %)보다 컸고, 배플 탱크에서도 강체가 능동 제어를 이겼다. 크기는
   슬로시 모델에 따라 갈려서 보수적인 얕은물 값을 믿는다. **한 줄 결론: 제어보다 탱크 설계가 먼저.**

> 말할 때 지킬 것: F8·F10 은 **합성 시연 조건**이지 녹화 주행이 아니다. 배플의 손실 계수가 실제
> 어떤 배플인지는 확인하지 못했다(F16). 둘 다 정직하게 말한다.

## 6. 시연 순서

플레이 씬 준비와 모든 키는 [operating-guide.md](operating-guide.md). 아래는 **무엇을 보여줄지**다.

1. **직접 운전(W/S, A/D)** — "적재 트럭" 느낌: 무겁고, 긴 제동, 느린 조향. `H` 로 HUD 자세히 보기는 평소엔
   꺼둔다(청중이 볼 것만 보이게).
2. **`Space` 로 스태빌라이저 끄고/켜고 하드 제동** — freeboard 바와 스필 카운터 비교.
3. **설정 패널(`` ` ``)에서 빗길 프리셋** — 교란을 키운다.
4. **`C` 3분할** — 데모의 하이라이트. 최신 녹화 주행을 ①②③ 로 동시에 재생하고 가장 적게 넘친 칸에 초록
   테두리. **보통 ① 강체가 이긴다.**
5. (선택) **`M` 얕은물** — 실제 파도가 벽을 타고 rim 을 넘는 모습.
6. (선택) **F8 예외** 보기 (아래), **청중 데이터로 재학습** (아래).

③ 칸이 "(offline→Hold)" 면 정책 서버가 없는 것이다. AI 성능이 아니라 "서버 없음" 표시다. 켜는 법은
[operating-guide.md](operating-guide.md) 7절.

### 청중이 운전한 데이터로 그 자리에서 재학습하기

`K` 패널로 청중 주행을 포함해 누적 데이터로 다시 학습한다(단계와 버튼은 operating-guide 8절).

**미리 알아둘 것 (정직하게 말할 부분):** findings F5/F6 대로, 청중이 자유롭게(급제동·코너링·요철 섞어서)
운전하면 재학습 후에도 십중팔구 **① 강체가 여전히 이긴다.** 버그가 아니라 이 프로젝트의 진짜 결론이다.
이 데모의 핵심은 "청중 데이터를 반영해 파이프라인이 다시 도는 걸 투명하게 보여주는 것"이지 "AI 가 극적으로
강체를 이긴다"가 아니다. 미리 그렇게 프레이밍해두면 결과가 뭐가 나오든 자연스럽다. 이전 정책 vs 새 정책
비교에 강체를 함께 넣는 이유도 같다 — 새 정책이 나아졌어도 강체에 못 미칠 수 있고, 그 맥락이 빠지면
오해하기 쉽다.

### F8 예외를 눈으로 보기 (권장 마무리)

같은 시연 주행(매끄러운 노면의 지속 코너링)의 스필 [L]:

| | 진자 | 얕은물 |
|---|---|---|
| ④ 천장 (후행지식) | **5.1** | **7.9** |
| ① 강체 | 7.9 | 24.9 |
| **③ 학습 정책** | **12.4** | 47.5 |
| ② 규칙기반 (PID / SFA) | 25.2 / 25.8 | 52.4 / 45.0 |

1. 메뉴 ▸ *FluidStabilizer ▸ **Generate Demo Drive (sustained corner)*** — 시연용 주행과 그 주행의 최적
   궤적을 `Traces/demo-corner-*.trace.csv` / `.traj.csv` 로 만들고 콘솔에 위 표를 찍는다. (합성
   조건이라 `datasets.tsv` 에는 넣지 않는다 — [reproducibility.md](reproducibility.md))
2. 플레이 씬에서 **L** 로 재생.
3. **0** (강체) → **5** (천장) 를 번갈아 눌러 스필 카운터 비교. **1/2** (규칙기반)도 눌러 보면 오히려 크게
   나빠진다. 정책 서버를 띄웠다면 **4** (학습 정책)도 — 규칙기반보다 확실히 낫고 강체보다는 못한 중간 위치다.
4. **M** 으로 얕은물로 바꾸면 차이가 훨씬 커진다 (24.9 → 7.9 L).

세 가지를 말한다: (1) 이길 수 있는 조건이 존재한다 — 지속 코너링은 저주파 단일축 외란이라 rate 제한
짐벌이 추종할 수 있고, 노면을 0.3× 만 켜도 이득이 사라진다(**광대역 노면**이 진짜 전제). (2) 지금의
규칙기반은 그 이득을 못 가져간다(강체보다 3배 나쁘고 토크를 94~100 % 포화). (3) 학습 정책이 그 간극을
절반쯤 메웠다 — 이 프로젝트에서 학습이 일어났다는 최초의 증거다.

**주의 — 정직하게 말할 것:** 5 번 레인(④)은 컨트롤러가 아니라 **주행 전체를 미리 알고 오프라인에서 계산한
최적해의 재생**이다. "이만큼은 가능하다"는 기준선이지(저대역 궤적 한정), 실시간으로 달성했다는 뜻이 아니다.

- **가장 가능성 높은 다음 걸음?** 배플 손실 계수가 실제 배플에 해당하는지 확인하는 것([lessons.md](lessons.md)

## 용어 (Physical AI 입문 청중용)

슬로시·freeboard·①~④ 같은 기본 용어는 [docs/README.md](README.md) "용어". 아래는 학습 관련 용어다.

| 용어 | 뜻 |
|---|---|
| **베이스라인 (baseline)** | 학습 정책과 비교할 기준. ① 강체, ② 규칙 기반. |
| **후행지식 (hindsight)** | 미래를 다 알고 나서(사후에) 최적화. 실제로는 불가능, 비교용 기준선. |
| **잔차 RL (residual RL)** | 정책이 베이스라인 행동 위에 *작은 보정*만 학습. 전부 배우는 것보다 안정적. |
| **행동 복제 (BC)** | 좋은 시범(여기선 후행지식 궤적)을 흉내내도록 지도학습으로 정책을 초기화. |
| **비대칭 actor-critic** | 학습 중 가치망(critic)은 ground truth 를 봐도 되지만, 실제 행동하는 정책(actor)은 센서만 본다. |
| **결정론 (determinism)** | 같은 입력 → 항상 같은 결과. 재현·디버깅·공정한 비교의 전제. |
