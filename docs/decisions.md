## D14 — 2026-10-16 — 프로젝트를 마무리한다: 탱크 설계가 먼저, 능동 제어 줄기는 종료

**결정 (소유자):** 추가 실험 없이 문서를 정리하고 마무리한다. 결론은 다음과 같다.

- 녹화 주행에서 ① 강체가 능동 제어(② 규칙기반, ③ 학습, 오라클 MPC)를 이긴다
  (F13, F14, F17).
- 탱크 설계(충전율·림 높이·배플)가 능동 제어보다 훨씬 크게 스필을 줄인다: 진자 모델 −9 ~ −98 %
  (F15), 얕은물 배플 −20 ~ −75 % (F16). 능동 제어는 −5 ~ −8 % (F14). 배플 탱크에서도 강체가
  능동 제어를 이긴다 (F17).
- 능동 제어 줄기(학습·MPC·감지기)는 닫는다. 재개 조건은 [experiment-plan.md](experiment-plan.md)
  "닫힘" 표.

**근거:**

- 같은 질문(어떻게 스필을 줄이나)에 대해 수동 해법이 능동 제어보다 큰 폭으로, 훨씬 싸게 답한다.
- 수동 해법의 크기는 슬로시 모델에 따라 갈린다(충전율 0.56: 진자 −98 %, 얕은물 −23 %). 정량은
  보수적인 얕은물 값을 쓴다 (F3 브래킷 규율).

**남은 한계 (결정이 아니라 사실):**

- 배플 손실 계수 K 와 실제 배플의 대응, 부분 높이·링 배플은 시험하지 않았다.
- F17 의 MPC 는 진자 내부 모델로 얕은물을 제어했다. 얕은물 내부 모델 MPC 는 시험하지 않았다.

**코드:** `ShallowWaterSloshModel` 이 스크린 배플(`BaffleCountX/Y`, `BaffleLossCoeff`)을 지원한다.
`SloshSweepRunner`(탱크 변경 스윕·감쇠 보정)와 `ActiveVsBaffleRunner`(능동 vs 배플)는 재현용
도구로 보존한다.

## D13 — 2026-10-12 — 인과 MPC 줄기를 닫는다

**결정 (소유자):** 오라클 MPC 가 중단 기준(−10 %)에 못 미쳤으므로(−5 ~ −8 %, [F14](findings.md))
인과 MPC 검증을 여기서 마무리한다. 상태 추정·얕은물 검증·학습(단계 2~4)은 진행하지 않는다.
phase-1 결론은 "녹화 주행에서 ① 강체가 이긴다"로 유지된다.

**근거:**

- 완전 상태와 정확한 내부 모델이라는 최선의 조건에서도 게이트 미달. 상태 추정 오차가 들어가면
  이득은 더 줄 가능성이 높다 (추정).
- 이득은 사건 뒤 자유 진동이 지배하는 주행 하나에 집중되고, 나머지 7 주행은 강체와 구분되지
  않는다. 이득의 원천은 감쇠가 아니라 "개입하지 않기"(시간의 약 55 % 잠금)였다.
- 설정 선택에 같은 8 주행을 썼고 인접 설정 간 변동이 ±8 % 라, 추가 튜닝으로 −10 % 를
  넘겨도 신뢰하기 어렵다.

**남은 코드:** `OracleMpcController`·`MpcEvalRunner`·`MpcSweepRunner`·`SpillDiagnostics` 는
상한 시험·진단 도구로 보존한다 (배포 불가, `IPrivilegedController`).

## D12 — 2026-10-11 — 미래 도로 정보는 쓰지 않는다 (다음 줄기였던 인과 MPC 는 D13 에서 종료)

> 인과 MPC 검증은 [D13](decisions.md) 에서 종료했다. 프리뷰 제외 원칙은 유효하다.

**결정 (소유자):**

- **프리뷰(미래 도로 정보)를 쓰지 않는다.** 실제 배포 환경의 AI 는 미래 도로를 모르는
  상태로 쓰인다. look-ahead 센서는 계속 보류한다 ([project-goals.md](project-goals.md)
  "현실성 제약"). "프리뷰를 준 천장과 인과 정책의 격차" 실험은 하지 않는다.
- **다음 줄기는 인과 MPC 검증이다.** 현재 상태와 모델·액추에이터 한계만으로 예측
  최적화하는 제어기를 만들고, 강체와 규칙기반 대비 상한을 잰다. 단계와 중단 기준은 [findings.md](findings.md) F14 에 있다.
  [experiment-plan.md](experiment-plan.md).

**근거:**

- ④ 천장은 0.1~0.3 Hz 저대역 궤적이라 슬로시 주기(피치 1.43 s, 롤 0.98 s — ROM 공식
  계산값)에 맞춘 능동 감쇠를 표현하지 못한다. "천장도 못 이겼다"(F5·F6·F13)는 능동 감쇠에
  대한 상한이 아니다.
- 기존 능동 제어기의 실패는 반응형이거나(F1·F4), 설계 모델이 실제 서보+지연+각도 명령
  플랜트와 달라 공진한 것(LQR)이었다. 액추에이터 모델을 포함한 예측 제어는 시도된 적이
  없다.
- 슬로시 주파수는 짐벌 대역폭(4 Hz) 안에 있고, 슬로시 상태는 로드셀·탱크 IMU 로 추정
  가능해 보인다 (추정 — 1~2단계에서 검증).

**기각한 대안:** 프리뷰 천장 곡선(원칙 위배), 학습 정책 추가 개선(F11·F12), 활성 구간
감지기(주행 40 개 이상 필요 — 보류), 배플 기준선(→ F15·F16·F17 에서 시험).

## D11 — 2026-10-11 — 이득이 없는 교사는 "잠금"으로 라벨한다, 그리고 BC/DAgger 줄기를 닫는다

교사를 12 합성 주행으로 늘리자(F11) 학습 정책이 학습 주행에서조차 강체보다 나빴다.
원인 중 하나는 라벨이었다: 내보내기가 모든 틱의 해제 요청을 +1 로 고정했기 때문에,
천장이 "아무것도 안 하는 게 최선"인 주행에도 "해제 + 속도 0" 을 가르쳤다. 해제된
서보는 잠긴 탱크가 아니다(F5).

**결정:**

- **유휴 교사 규칙.** 천장이 강체를 max(0.5 L, 10 %) 이상 못 이기는 주행은 교사
  궤적을 정확히 0 으로 만들고(`MultiCornerRunner`), BC 내보내기는 0 궤적 교사에 잠금
  라벨(해제 요청 0)을 붙인다(`BcDatasetExporter`). 가드:
  `ExplicitLock_IdleTeacherLabelsLocked_ActiveTeacherLabelsRelease`.
- **합성 교사는 별도 매니페스트.** `datasets-f8-multi.tsv` — 녹화 주행용 `datasets.tsv`
  분할(train / validation / final)과 섞지 않는다.
- **배포측 해제 보정은 실험 도구.** `serve_policy.py --release-bias / --release-ema`
  는 기본 꺼짐이고, 켜면 정책 식별 문자열에 기록된다(실행 증거에서 구분 가능).
- **BC / DAgger 줄기를 닫는다.** 근거: F11 (교사 늘리기 무효), F12 (DAgger 가 손실은
  줄이나 강체를 못 이기고 분산 큼), F13 (소유자 홀드아웃에서 ③ 이 강체보다 5~15 % 나쁨).
  재개 조건은 [experiment-plan.md](experiment-plan.md) "앞으로 할 수 있는 것" 표.

**기각한 대안:** 교사 주행을 더 늘리기(F11 의 구조적 원인이 그대로), DAgger 시드·반복
확대(분산이 크고 평균이 강체 아래로 내려가지 않음), 해제 임계 상향(편향이 크면 정확히
강체와 같아질 뿐 이득이 없음).

## D10 — 2026-09-11 — 잠금은 dead-band 가 아니라 정책이 요청한다 (D8 수정)

D8 은 lock-capable 액션으로 F5 의 구조적 핸디캡을 없앴지만, **잠금 여부를 합성된
rate 로부터 사후 판정**했다. finding F9 가 그 대가를 측정했다: 잔차 액션 공간이
**절벽**이 된다 — dead-band 안에서는 행동 효과가 정확히 0(학습 신호 없음), 넘으면
스필 2.4 배, 사이에 기울기가 없다. 가우시안 정책의 꼬리가 문턱을 넘나들어 절벽
아래로 착지한다.

**결정: 잠금을 정책의 명시적 선택으로 만든다.**

- **3번째 액션 = 해제 요청.** 학습 안 된 네트워크의 출력 ≈ 0 이 곧 잠김 = 강체다.
  우리가 가진 최선의 해석적 결과를 정책이 공짜로 받는 게 맞다.
- **시작을 잠긴 상태로.** 체결이 0.5° 이내에서만 가능하므로, 시작 후 서보가 관절을
  움직이면 다시는 잠글 수 없는 **일방통행**이었다 — 정책이 잠금을 못 배운 진짜 이유.
- **해제 요청을 저역통과** (gain 0.1 ≈ 10 틱, 문턱 0.5). 기계식 잠금을 100 Hz 로
  재결정하지 않는다. 이게 없으면 에피소드가 ~2500 번의 독립 추출이라, 평균이
  "잠금 유지" 인 정책도 즉시 해제를 뽑는다.
- **관측에 잠금 상태 추가** (frame 39 → 40, `obsVersion` 2). 컨트롤러 자신의
  상태이지 특권 정보가 아니다.
- 물리 제약(0 각도 체결, 최소 유지 틱)은 **그대로** 둔다. 학습 편의로 기계를
  거짓말시키지 않는다.

**결과 (F10):** 절벽이 진짜 바닥이 됐다 — 해제를 요청하지 않는 한 잔차가 무엇이든
스필이 강체와 정확히 같다 (③ ⊇ ① 이 a = 0 뿐 아니라 전 구간에서 성립). 그리고
③ 이 처음으로 학습해 규칙기반을 51 % 앞섰다.
가드: `ExplicitLock_KeepsTheRigidFloor_ForAnyResidual`.

## D9 — 2026-09-10 — 정책 행동 계약을 한 곳에 (PolicyContract)

학습(`RlEnvironment`)은 `baseline + policy·0.35·maxRate` 를 만들어 lock gate 를 통과시켰는데, 배포
(`RemotePolicyController`)는 `policy·maxRate` 만 보냈다. 잔차 정책을 브릿지로 서빙하면 학습 때와 완전히 다른 의미로
실행됐고, 관측도 1 틱 어긋나 있었다.

**결정:** 행동 합성 규칙을 하나의 타입(`PolicyContract` + `ActionComposer`)으로 묶어 **학습과 배포가 같은 것을 쓰고**,
계약이 체크포인트를 따라다니게 한다. 계약이 없거나 맞지 않는 정책은 조용히 실행하지 않는다(레거시 경로 +
`policy-unverified`, 또는 거부 + `hold-fallback`). 관측 정렬은 배포 쪽에 맞췄고, 이전 체크포인트는 재학습 대상이다.
구현·전달 경로·BC 목표 변환: [rl.md](rl.md) "행동 계약".

**가드:** `PolicyContractParityTests` — 같은 초기조건·결정론적 정책에서 학습 환경과 브릿지 경로의 스필·freeboard·명령
rate·스텝 수가 모두 일치해야 한다. 인코더 클래스가 같다는 것은 근거가 아니다.

## D8 — 2026-08-30 — lock-capable 하이브리드 액션 공간 (F5 전제 조정)

> **현재 상태 (D10 이후):** 잠금 판정은 아래의 rate 데드밴드가 아니라 정책의 세 번째 액션(해제 요청)이 맡는다.
> 액션은 3차원이고, ③ ⊇ ① 은 행동이 정확히 0 일 때만 성립했다(F9). 아래는 결정 당시의 서술이며 `LockGate`
> 인프라와 물리 제약은 그대로 쓰인다.

F5: 완전한 후행지식 짐벌 궤적조차 녹화 주행에서 기계적으로 잠근 탱크(①)를 이기지 못한다. 근본 원인은 *능동*
컨트롤러의 "hold" 가 강체 관절이 아니라 슬로시 모멘트에 눌려 처지는 위치 서보라는 점이다. 0 을 명령해도 이미 잠근
관절보다 ≈ 5~7 L 더 진다(`무동작` 25 L 대 `잠금` 19 L). F5 가 든 전제 조정 중 하나가 "능동 보정이 필요할 때만 빼고
기계적으로 잠그는 하이브리드 액션 공간"이었다.

**결정.** 합성된 관절 속도 명령에 데드밴드와 히스테리시스를 가진 게이트(`LockGate`, 엔진프리 결정론적 상태기계)를 둔다.
합성 rate 가 `LockRateThresholdRadPerSec`(기본 0.06) 미만이고 두 관절이 `LockAngleThresholdRad`(기본 0.5°) 이내면
`Locked` 명령을 발행한다(구조가 모멘트를 받고, 토크 0, 권선은 식는다). 일단 잠기면 rate 요구가 문턱의
`UnlockRateFactor`(2.5 배)를 넘고 `MinLockDwellTicks`(8)가 지나야 능동 모드로 전환한다. 게이트는 전부 C# 컨트롤러 쪽에
있어 액션 차원, wire 포맷, Python 학습기는 바뀌지 않았다(당시). 기본은 꺼짐이라 기존 결정론 가드와 테스트는 그대로다.
보상은 바꾸지 않는다 — Locked 일 때 `AppliedTorque = 0` 이라 effort 항이 자동으로 0 이고, 잠금 보너스는 reward hacking 의
여지만 넓힌다.

**기대한 효과.** ③ 의 바닥이 처지는 서보(25 L)가 아니라 강체 탱크(19 L, = ①)가 되어 ③ ⊇ ① 이 성립하고, "학습이 강체를
이긴다"가 구조적으로 가능해진다. 두 레인의 구분이 흐려지는 절충은 받아들인다.

**결과 ([F6](findings.md), 2026-08-30):** F5 의 구조적 핸디캡은 없어졌다(무동작 바닥 25 L → 잠근 Hold 19 L). 그러나 2c
스윕 11 개 운영점에서 hindsight 는 여전히 강체를 이기지 못했고(강체가 넘치는 모든 fill 에서 회복 1~2 %), 잔차 RL 은
시작하지 않았다. 세부: `LockGate.cs`, `GimbalConfig` 의 `Lock*` 필드, 가드 `LockCapableActionTests` (8).

## D5 — 2026-08-28 — `Hold` 는 잠근 관절; 액추에이터 크기 재조정, 열 한계 강제

F3 부록(`Hold` 위치 서보가 공격적 기동 중 실제 슬로시 모멘트에 눌려 ~30° 까지 포화·처짐)에 이은, 서로
연결된 두 결정이다.

**1. `Hold` = 0 을 명령하는 서보가 아니라 기계적으로 잠근 관절.**
새 `StabilizerCommandMode.Locked`: 두 관절을 모두 0 에 고정하고, 슬로시 모멘트는 차체 구조(v1 에서는 무한
질량, D1)가 받는다. 액추에이터는 토크를 쓰지 않으므로 포화·처짐·발열이 불가능하다. `HoldController` 가 이를
발행한다. 이것이 진짜 "능동 안정화 없음" 바닥이며, 모든 컨트롤러와 RL 정책이 진짜 강체 탱크를 상대로
채점된다. 이유: "0도 각도 홀드" 방식은 "스태빌라이저 없음"과 "약한 스태빌라이저"를 혼동했고, F2 의 헤드라인
결과가 그 부산물이었다(F4 참고).

**2. 현실성을 위해 액추에이터 크기를 재조정하되, 출력 부족은 의도된 과제로 유지한다.**
소유자의 프레이밍: 권한이 제한된 것이 요점이다. Physical AI 는 실제 로봇의 제약을 극복해야 한다. 다만 값이
*그럴듯*해야 하고, 준정적 범위조차 버티지 못하는 스태빌라이저는 그렇지 않다.
- `MaxTorqueNm` 650 → **900**. 0.45 g friction-circle 한계에서 최악의 준정적 슬로시 모멘트는 ≈ 740 N·m
  이다. 900 은 약 20 % 의 여유로 이를 덮지만, 공격적인 *동적* 틸트 추종에는 여유가 없다.
- `ContinuousTorqueNm` 280 → **420**, 이제 **강제된다**: `GimbalActuator` 의 I²t 권선열 모델(상태
  `Thermal ∈ [0,1]`, `ThermalTimeConstantSeconds` = 15 s). 연속 값을 넘는 토크는 권선을 데우고, 쓸 수 있는
  피크가 900 에서 420 쪽으로 낮아진다. 연속 값 이하에서는 식는다. 순간적인 몰아쓰기는 공짜이고 지속적인 강한
  기동은 아니다. 정책이 관리해야 하는 명시적 권한 예산이다. `Thermal` 은 `GimbalAxisState` 와
  `PrivilegedObservation` 에 노출된다.

결과(F4): 강체 `Hold` 를 상대로 어떤 분석적 반응형 틸트 컨트롤러도 어느 시나리오에서도 이기지 못한다.
강체를 이기려면 예측이나 학습이 필요하다.

## D4 — 2026-08-28 — 얕은물 슬로시 모델: 스킴과 커플링 선택

`ShallowWaterSloshModel`(design-review §6 의 옵션 D)은 바뀌지 않은 `ISloshModel` 인터페이스 뒤에 있는
2-D 깊이평균 Saint-Venant 솔버다. 내린 선택:

- **스킴.** 1차 유한체적, **Rusanov (local Lax–Friedrichs)** flux, forward Euler, 명목 탱크에서 약 48×28
  격자(목표 셀 크기 ~25 mm). 반사 벽(정수압만 통과)이고, 벽 셀이 rim 을 넘으면 weir overflow 로 처리한다.
  정확도보다 견고성과 양수성(positivity) 보장을 택했다. 수치적으로 확산성이지만 1차 모드가 파장당 ~90 셀로
  해상되므로 주파수는 여전히 진자 모델과 ±15 % 이내다. MUSCL/제한 재구성은 나중에 결과가 더 약한 감쇠를
  요구하면 바꿔 끼울 수 있다.
- **결정론.** 600 Hz 틱마다 서브스텝 수 = `ceil(1.5·dt·s_max/CFL)`(CFL 0.40)이고, 이는 필드의 결정론적
  함수다. wall-clock 도 스레딩도 쓰지 않는다. 하드 클램프(h ≥ 1e-6, |u| ≤ 8 m/s)는 진자 모델의 anti-NaN
  가드와 같은 역할이다.
- **프레임.** 내부 격자의 원점 = **탱크 바닥 중심**이며, `PendulumSloshModel` 의 유효 규약과 같다(진자도
  바닥 중심 기준 토크를 반환한다). 실제 짐벌 피벗 높이가 토크 기준이 되어야 하면 두 모델이 함께 바뀐다.
- **반응(D3 적용).** 솔버는 탱크 각가속(Euler) 항을 포함한 *실제* 운동을 적분한다. 탱크로 되먹이는 반응은
  **준정상(quasi-steady)** 이다. 셀마다 Σ mₖ·(g − a_O − ω×(ω×r) − 2ω×v_rel), 즉 액체 질량분포 × 체적력이며
  Euler 항은 뺀다. 그 항은 진자 모델이 쓰는 *같은* 분석적 등가역학 추정에서 계산한 상수 **reflected
  inertia** 로 전달한다. 그래서 액추에이터는 두 모델에서 같은 회전 하중을 느끼고, 파동 동역학만 다르다.
  파동 자체가 벽에 주는 운동량 flux(2차 반응 보정)는 v1 에서 되먹이지 않는다.
- **파도 깨짐 + rim run-up**(findings F3 스테이지 1 이후 추가). NLSW 는 파도를 깰 수 없어 벽 run-up 을 과대
  예측한다. 두 가지를 추가했다. (1) 파도 깨짐 와류 점성: 약 31° 보다 가파른 front 에서 확산성 운동량 flux
  `ν = C·Δ·√(g·h̄)·ramp`(Kennedy et al. 2000, slope trigger), `C = 0.6`. (2) weir overtopping head 를 셀별
  저역통과 경계면(`τ = 0.2 s`)에서 측정한다. 벽을 치고 물러나는 순간적인 slap 은 거의 스필하지 않는다. 상수는
  문헌 범위 안이다. `HighwayBriskLowFreeboard` 의 판정이 여기에 약간 민감하다(findings F3).
- **`SloshParameters` 중 쓰지 않는 것:** `ParticipatingMassScale`(필드에 이미 반영되어 있고, reflected
  inertia 추정에서는 제외), `SurfaceSlopePerPendulumAngle`(실제 표면이 있다). `NaturalFrequencyScale` 은
  중력파 항만 스케일한다.
- **`ModeState`** 는 평균 자유표면 기울기에서 *등가* pitch/roll 슬로시 각과 rate 를 보고한다(특권
  베이스라인이 계속 동작하도록).

진자 ROM 이 대량 RL 의 기본으로 유지된다(더 싸다). 얕은물은 정밀도 점검용이자, 선택적인 고정밀 평가·학습
모델이다.

## D3 — 2026-08-28 — 슬로시 ↔ 액추에이터 커플링: 관성 vs 하중 분리

슬로시 모델과 짐벌 액추에이터는 서로 영향을 주는 양방향 결합이다. 슬로시의 전체 반응 토크를 액추에이터의
외부 하중으로 그대로 먹이면 불안정한 명시적 대수 루프가 생긴다(반응의 각가속 항이 음의 관성처럼 작용한다).
해결:

1. **반응을 분리한다.** 슬로시 모델이 축별로 대략 상수인 `ReflectedInertia*` 를 보고하고
   (`IReflectedInertiaSource`), 시뮬이 이를 액추에이터 축 관성에 더한다. 그러면 모델이 매 스텝 돌려주는 반응
   토크는 탱크 각가속 항을 빼고 상태 의존(θ, θ̇, base 운동) 외란만 남으며, 한 스텝 지연된 외부 하중으로
   되먹여도 600 Hz 에서 안정하다.
2. **짐벌 운동 중에는 피벗이 평행이동하지 않는다.** `TankKinematics` 는 피벗의 선가속을 차체 운동만으로
   계산한다. 짐벌 피벗은 회전 중심이라 관절 rate/accel 이 피벗을 움직이지 않는다. 포함하면 큰 lever-arm
   (≈2.6 m)의 되먹임이 슬로시 모델에 들어간다.
3. **액추에이터는 순수 rate 루프가 아니라 위치 서보다.** 명령된 rate 가 위치 setpoint 로 적분되고 PD+I
   루프가 이를 추종한다. 그래서 정상 상태의 외부 하중은 drift 가 아니라 유한한 처짐(sag)을 만든다.

진자의 각과 rate 는 ROM 유효 범위(~75°, 25 rad/s)로 클램프해서, 나쁜 과도 현상이 NaN 으로 번지지 않게
한다. 정상 사용 중에 클램프에 걸리면 유효 범위를 벗어난 시나리오라는 신호다.

## D1 — 2026-08-27 — 기계 시뮬레이션은 PhysX 가 아니라 매니지드 코드로

**결정.** 문제의 강체 동역학 전체(차량 스프렁매스 운동, 2축 짐벌, 슬로시 모델)를 `FluidStabilizer.Core`
의 평범한 C# 로 고정 **600 Hz** 스텝에서 적분한다. Unity PhysX 는 어떤 시뮬레이션 동역학에도 **쓰지
않는다.** `FluidStabilizer.Sim` 은 시각화, 입력, 씬 배선에만 Unity 를 쓴다.

600 Hz 인 이유는 200 Hz 센서가 정수로 나누어떨어지게 하려는 것이다
([frames-units-conventions.md](frames-units-conventions.md)).

**이유.**

- **Mac 과 Windows 사이의 결정론.** Unity 의 PhysX 는 같은 머신·같은 빌드에서만 재현된다. 플랫폼을 넘는
  비트 단위 재현성은 보장되지 않는다. 설계 리뷰는 결정론을 상위 5 대 리스크로 꼽았고, 소유자는 두
  플랫폼에서 개발할 계획이었다. seeded RNG 를 쓰는 매니지드 고정 스텝 적분기는 어디서나 비트 단위로 같다.
- **시스템이 작다.** 차량 heave/pitch/roll + 종/횡 운동학(~10 상태), 짐벌 관절 2 개 + 액추에이터 내부
  상태(~8), 슬로시 진자 2 개(~4). 합쳐서 약 20 개의 상태 변수라서, 직접 만든 semi-implicit / RK4 적분기가
  600 Hz 에서 쉽게 감당한다.
- **설계가 이미 이쪽을 가리킨다.** 직접 만든 3-DOF 스프렁매스 차량(WheelCollider 가 아님)과 PhysX 밖에서
  적분하는 슬로시 ODE 를 요구한다. "직접 만든 것"을 기계 코어 전체로 넓히면, PhysX 바디와 매니지드 슬로시
  ODE 사이의 이음매가 없어진다. 솔버 노이즈와 커플링 버그가 숨는 곳이 바로 그 이음매다.
- **속도와 테스트 용이성.** RL 스텝 루프에 물리 엔진이 없으므로 초당 시뮬레이션 스텝이 늘고, 전체
  시뮬레이션을 Unity 프로세스 없이 단위 테스트할 수 있다(엔진프리 어셈블리에 있다).

**비용 / 리스크.**

- 자체 접촉/도로 모델과 짐벌 관절 동역학을 직접 작성해야 한다. 정밀도를 일부러 낮게 유지하고(설계 리뷰
  §8–§9), 테스트에서 분석 가능한 케이스로 검증해 완화한다.
- 탱크가 짐벌을 통해 차량에 운동학적으로 붙어 있어서, v1 에서는 슬로시 힘이 차량을 움직이지 않는다(트럭
  질량 ≫ 탱크 + 액체). 슬로시는 짐벌 액추에이터와 로드셀에는 하중을 준다. 이 근사는 문서화되어 있고 다시
  검토할 수 있다.

**레이아웃 결과.** `FluidStabilizer.Core` 가 시뮬레이션 루프와 물리 서브시스템도 담는다. `Sim` 은 얇은
Unity 껍데기로 줄었다.
