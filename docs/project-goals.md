# 프로젝트 개요와 목표

> 이 프로젝트의 **의도와 범위에 대한 유일한 출처.** 다른 문서와 어긋나면 이 파일이 우선한다.

## 진짜 목적

이 프로젝트의 요점은 **Physical AI 파이프라인 전체를 처음부터 끝까지 직접 만들면서 배우고 이해하는 것**이다.
지금 실제 로봇을 사는 것은 현실적이지 않아서 시뮬레이션이 로봇을 대신한다. 완성된 산출물보다, 모든 층을 직접
만들고 이해했다는 사실이 더 중요하다. 물리 → 센서 → 액추에이터 → 컨트롤러 → 학습 정책 → 평가 → (나중에)
실제 하드웨어.

아래의 모든 것이 이 목적에 복무한다. 어떤 선택이 시스템을 더 인상적으로 만들지만 덜 이해하기 쉽게 만든다면,
그것은 잘못된 선택이다([CLAUDE.md](../CLAUDE.md) — "소유자" 참고).

## 구체적 과제

AI 가 **사람이 운전하는 트럭에 실린 뚜껑 없는(개방형) 액체 탱크** 아래의 2축(pitch/roll) 스태빌라이저를
제어해서 액체가 넘치지 않게 한다. AI 는 운전하지 않는다. 운전자는 외부 외란이다. 어려운 부분은 **비이상적인
액추에이터**로, **부분 관측** 아래에서, **슬로시의 시간 동역학**을 다루는 것이다. AI 는 숨겨진 액체 상태를
추론하고 파도보다 앞서 행동해야 한다.

처음 정한 물리 현실성 변수(고정된 목록은 아니며, 무엇이 실제로 중요한지는 설계 리뷰가 판단한다): 탱크 질량 ·
액체량 · 액체가 움직이면서 생기는 순간적인 CoM 이동 · 하중과 관성에 따른 액추에이터 응답 변화 · 최대
토크/각속도/travel 각 · 기어비 · 백래시 · 마찰/기계 효율 · 제어 지연.

## 센서 원칙

AI 는 **실제 센서로 얻을 수 있는 값만** 관측한다. 후보: 차량 IMU **와** 탱크 IMU(분리해서 유지한다 — 예를
들어 언덕에서 자세와 차량 운동을 각각 실제 센싱으로 얻어야 한다) · 로드셀 · 스태빌라이저 엔코더 · 모터
전류/토크 추정 · (선택) 제한적인 액체 레벨 센서.

Unity 의 ground truth 는 **디버깅과 평가에만** 쓴다. AI 관측에는 실제 센서가 줄 수 없는 정보가 **절대 들어가면
안 된다**: 모든 액체 입자의 위치, 정확한 순간 액체 CoM, 트럭의 미래 운동, 운전자의 미래 입력, 다가오는 도로,
물리 엔진 내부 상태.

## 비교 대상과 지표

같은 시나리오, 같은 지표(스필 리터)로 네 가지를 비교한다. 용어는 [docs/README.md](README.md) "용어" 참고.

| # | 설정 | 구현 |
|---|---|---|
| ① | 탱크를 트럭에 강체로 고정 (스태빌라이저 없음) | `HoldController` = 기계적으로 잠근 관절 (D5) |
| ② | 고정된 규칙으로 탱크 틸트 (specific-force alignment / PID) | `SpecificForceAlignmentController`, `PidController` |
| ③ | **사람 운전으로 (부분) 학습한 Physical AI** | 교사 → BC → 배포 (`serve_policy.py`) |
| ④ | 오프라인 후행지식 천장 — 주행 전체를 아는 **저대역(0.1~0.3 Hz) 궤적**의 최선 스필 | `HindsightOptimizer`. 슬로시 주기(~1 s)마다의 능동 감쇠는 표현하지 못하므로 **모든 인과 제어기의 상한은 아니다** |

목표는 중요한 조건(실제 도로에서의 현실적인 운전)에서 **③ 이 ①, ②, ④ 와 어떻게 비교되는지**에 대해 방어할 수
있는 결론을 내리는 것이다. **목표는 "③ 이 이긴다는 것을 증명"하는 것이 아니라** 파이프라인 전체를 만들고,
이해하고, 발견한 것을 정직하게 보고하는 것이다(소유자의 재정의, 2026-08-29).

결과와 교훈은 [lessons.md](lessons.md), 숫자의 근거는 [findings.md](findings.md), 프로젝트를 마무리한 결정은
[D14](decisions.md) 에 있다. 이 문서는 결과를 담지 않는다.

## 최종 제품 아키텍처 (소유자 결정 2026-08-29)

**원칙:** 정책을 Unity 안에 구워 넣지 않는다. 그렇게 하면 "AI"가 "세계" 안으로 뭉개져 학습 목표를 해친다.
실제 로봇은 뇌·몸·학습 장비를 **링크로 대화하는 별개의 것들**로 둔다. 시뮬도 그렇게 한다. 이렇게 만드는 것
자체가 sim-to-real 준비다.

```
┌──────────────────────────┐   ┌───────────────────────┐   ┌────────────────────┐
│  세계 + 몸체              │   │  뇌                   │   │  학습 장비          │
│  Unity 앱 (컴파일됨)      │   │  정책 추론 프로세스    │   │  Python, 오프라인   │
│                          │   │  (Python)             │   │                    │
│  • 차량 + 도로 + 탱크     │◄─►│  • 학습된 체크포인트   │   │  • PPO / 잔차 RL    │
│    + 슬로시 + 액추에이터  │TCP│    로드                │◄─►│  • BC 웜스타트      │
│  • 센서 OUT, 명령 IN      │(= │  • obs 입력 → 행동     │TCP│  • 실험 관리        │
│  • ① 강체 = 기계적 설정,  │ROS│    출력, 결정론적       │   │  • 작은 GUI (보류)  │
│    여기 있음              │ 2)│  • 이게 "온보드 컴퓨트"│   │                    │
│  • ② 규칙기반 = 엔진프리  │   └───────────────────────┘   └────────────────────┘
│    C# IController,        │       ▲ 브릿지는 눈에 보이는 일급 요소:
│    이식 가능 (지금은      │       │ obs 가 나가고, 행동이 돌아오고, reward 가
│    in-process)           │       │ 쌓이는 것을 볼 수 있다 — 파이프라인이 읽힌다
│  • 모든 설정용 컨트롤 패널│
└──────────────────────────┘   ONNX(또는 평범한 가중치 파일)는 학습된 정책을
                               뇌에 넘기는 교환 포맷이다 — Unity 바이너리에 굽지 않는다.
```

설계 의도:

- **Unity = 플랜트(plant).** 컴파일된 앱이 세계이자 로봇 몸체다: 물리, 도로, 탱크, 슬로시, 액추에이터,
  센서, 수동 주행 모드, 평가 하네스, 컨트롤 패널. 센서 메시지를 발행하고 명령 메시지를 소비한다. ① 강체는
  *기계적* 설정이고 여기에 있다. 학습 정책은 **들어 있지 않다.**
- **정책은 자기 프로세스로 실행한다**(지금은 `serve_policy.py`). 브릿지로 연결하며, 실제 로봇의 온보드
  컴퓨트 ↔ 센서/액추에이터 링크에 해당한다. 비교에서 ②(엔진프리 C# `IController`)는 단순해서 in-process 로
  돌지만 같은 외부 형태로 옮길 수 있다. ③(학습)은 항상 외부 추론 프로세스다.
- **학습기는 별개이고 오프라인이다.** 헤드리스 Unity 인스턴스와 브릿지로 대화한다. 완성된 데모와 함께 돌지
  않는다.
- **ONNX 는 교환 포맷**이지 Unity 안의 런타임 대상이 아니다. "학습 장비"에서 "뇌"로 넘기는 용도다. 초안
  단계에서는 직접 만든 가중치 파일도 허용한다.
- **주요 설정은 Unity 컨트롤 패널에 둔다** — 시나리오, fill, 도로 강도, 컨트롤러, 운전자, seed,
  run/record/evaluate, 실시간 지표(배플 같은 세부 값은 코드와 실험 도구에서 바꾼다). `-executeMethod` /
  `-rl*` 플래그와 `experiment.txt` 는 스크립트용 뒷문으로 유지한다.
- **브릿지가 보이게 한다.** 세계와 뇌 사이의 데이터 흐름을 지켜보는 것이 Physical AI 시스템을 이해하는 가장
  좋은 방법 중 하나다.

받아들인 트레이드오프: 완성된 데모는 "Unity 앱 **과** 정책 프로세스를 함께 실행"하는 것이며, 자기완결적인
`.exe` 하나가 아니다. 학습/포트폴리오 산출물로서는 아키텍처를 보여 주는 특징이지 후퇴가 아니다.

## 현실성 제약 (첫날부터 포함)

이미 포함한 것: 고정 스텝 결정론, 지연, 센서 노이즈/바이어스, 액추에이터 토크/rate/travel/열 한계(백래시는 구현했으나 기본 꺼짐),
브래킷 규율을 가진 슬로시 모델 2종(얕은물은 스크린 배플 지원), friction-circle 차량, 도로(완만한 grade, 커브
bank, 노면 거칠기, 이산 범프/포트홀) + 서스펜션 heave DOF([road-model.md](road-model.md)). 강체 탱크는 모든
범프를 액체에 전달한다 — ③ 이 이기기를 기대한 외란이었으나 녹화 주행에서는 이기지 못했다
([F13](findings.md)).

보류: ROS 2, ML-Agents, 입자/SPH 유체, 완전한 타이어 모델, look-ahead 센서, 사실적인 렌더링,
hardware-in-the-loop.

## 설계 원칙

- 시각적 사실성보다 물리적 **인과 일관성**.
- 더 정밀하다는 이유만으로 비싼 방법을 고르지 않는다.
- RL 이 충분한 시뮬레이션 스텝을 모을 수 있어야 한다.
- AI 관측과 시뮬레이션 ground truth 를 분명히 분리한다.
- Sensor → Controller → Actuator 경계를 지킨다. 인터페이스는 실제 하드웨어로 교체할 수 있게 한다. 컨트롤러를
  Unity 구현에 강하게 결합하지 않는다.
- "한 번의 주행" = 녹화한 사람 트레이스 + 고정된 도로 seed(결정론적이고 재현할 수 있다). 경로/웨이포인트/맵
  시스템은 두지 않는다 — AI 는 운전하지 않는다.
- 헤드라인 벤치마크는 녹화 주행(주행별 리터, 슬로시 2종)이다. 합성 시나리오는 회귀 신호용이며 헤드라인이
  아니다.
- 소유자가 지명한 기술이라도 무비판적으로 채택하지 않고, 더 나은 대안을 제안한다.
- 첫 구현은 단순하게 하되, 나중에 통째로 버려야 할 것을 만들지 않는다. 미래를 위해 과하게 추상화하지도
  않는다.

## 채택하지 않은 것

ROS 2, Unity ML-Agents, 유체 시뮬 플러그인(Obi, Zibra), CFD, 완전한 WheelCollider 차량 시뮬,
`com.unity.sentis`, 클라우드/CI 인프라는 명시적 결정 없이 설치하지 않는다. "나중에 필요할 테니 지금 설치"는
하지 않는다. 목록과 근거는 [CLAUDE.md](../CLAUDE.md) 와 [design-review.md](design-review.md) §21 에 있다.
